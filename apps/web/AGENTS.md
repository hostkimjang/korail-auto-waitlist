# 웹 프로토타입 작업 지침

## 확정된 제품 디자인 방향

- 2026-07-29 기준 ImageGen 시안 2번을 선택했다. 시안 1번과 3번 방향은 사용하지 않는다.
- 메인은 소비자 앱 형태이며 모든 `payment_required` 작업과 공식 결제 행동을 가장 높은 우선순위로 둔다. 운영사가 timezone-aware `payment_deadline`을 제공한 작업만 실제 남은 시간을 표시하고, 값이 없으면 임의 카운트다운을 만들지 않는다. 복수 결제 작업은 실제 기한 오름차순으로 모두 표시하고 각 작업의 공식 결제 CTA를 유지한다.
- 모바일 PWA와 PC 웹을 같은 정보 구조로 반응형 지원한다. 모바일에서는 결제 카드와 CTA가 첫 화면에 남고, PC에서는 왼쪽 내비게이션과 넓은 작업 영역을 사용한다.
- 시스템 요청 수, worker, cooldown 같은 기술 정보는 홈에 노출하지 않고 `설정 > 로그·진행 상태`로 분리한다. 근거가 없는 서버 오류율이나 worker 상태를 0%·정상으로 추정하지 않고 `기록 없음` 또는 `확인 불가`로 표시하며, 원문 로그·오류 문자열·payload·식별정보는 이 화면에 노출하지 않는다.
- 홈의 활동 중 대기는 고정 개수 제한이나 `slice` 없이 전부 표시한다. 만료·완료·실패 등 비활성 기록은 활동 목록에 섞지 않고 `전체 내역 보기`를 통해 `내 예약`에서 확인한다.
- 시각 원본은 저장소 루트 `docs/design/selected-responsive-ui.png`이다. 경쟁 앱 이름이나 로고는 복제하지 않고 자체 명칭 `레일웨잇`과 자체 앱 아이콘을 사용한다.
- 열차 결과 카드는 시간표·조회 시각·운임·소요시간과 일반실·특실별 상태 패널을 분리해 보여주되 사용자 화면에는 내부 수집원 이름 `TAGO`를 노출하지 않는다. 관측 provenance가 유효할 때만 세부 상태를 `예매 가능`, `매진`, `예약대기 가능`, `예매 불가`로 표시하고, 관측되지 않은 두 등급은 status와 관계없이 `unknown`과 `확인 필요`로 표시한다. SRT 1인 사용자 트리거 조회의 열차번호·날짜·출발시각 exact match는 좌석별 관측값으로 표시하되 다인원·상류 실패·불일치는 `확인 필요`를 유지한다.
- 좌석별 상태 payload는 status만 신뢰하지 않는다. `official_provider`, `user_confirmed_official_page`, `mock` provenance에 source와 `observed_at`이 없거나 계약이 잘못되면 `unknown/not_observed`로 fail-closed하고, mock은 `벤치마크 데모 상태`로 명시한다. 사용자 직접 확인값은 고정 source와 미래의 `fresh_until`이 모두 있어야 하며 `공식 페이지에서 직접 확인`으로 구분한다.
- KORAIL·SRT 열차 단위 `좌석 상태 입력`은 공식 화면을 사용자가 직접 확인한 뒤 명확히 본 일반실·특실 상태만 한 번에 저장한다. 열차 identity와 인원은 수정할 수 없고, 하나 이상의 등급을 선택해야 하며 성공 후 현재 시간표 query만 재조회한다. 입력값을 provider 관측값이나 자동 예약 근거로 표현하지 않는다.
- 일반실·특실은 2열 좌석 패널에서 각각 선택할 수 있게 하고 버튼 이름에 좌석 등급과 행동을 포함한다. 선택 상태는 `aria-pressed`로 전달하며 색상이나 벨·시계 아이콘만으로 상태·행동을 표현하지 않는다.
- 열차 등록 화면은 시간표를 처음 열거나 날짜·시간 범위를 바꿀 때 서버가 일반실·특실 상태를 함께 조회해 자동 반영한다. 브라우저 확장 설치나 별도 가져오기 행동을 요구하지 않으며, 기본 설정 화면에도 레거시 확장 연결·pairing UI를 노출하지 않는다. 미관측·상류 오류일 때만 서버 재조회 버튼을 fallback으로 제공하고, 미관측 좌석은 대기 등록을 막는다. 예매 가능·매진임박·입석+좌석은 공식 예매와, 유효한 evidence 및 실행 `seat_monitoring` capability가 있을 때 선택 좌석별 감시 등록을 함께 제공한다. 매진은 취소표 대기, 예약대기 가능은 공식 예약대기로 구분하며 KORAIL·SRT는 각각의 3중 opt-in에서만 대기 행동을 발급한다. 예약 실행은 별도 1회 gate·로그인 확인된 계정·작업 정책까지 충족할 때만 열린다.
- 공식 채널 인계는 안정적인 공식 HTTPS 링크와 비밀값이 없는 여정 정보 복사로 제공한다. 공식 페이지가 여정을 자동 입력한다고 가정하거나 링크 열기를 좌석 확인·예약 성공으로 처리하지 않는다.
- `OfficialHandoff`는 운영사별 고정 진입점만 열고 provider action URL은 동일 origin·경로 검증 뒤에도 고정 URL로 정규화한다. 선택한 좌석 등급의 provenance만 설명하며, 복사는 명시적인 `true` 반환만 성공으로 보고 `false`·예외·무응답은 모달 안의 읽을 수 있는 실패 요약으로 처리한다. 처리 중에는 중복 복사를 막고, 닫기·재열기 전의 오래된 비동기 결과가 새 dialog 상태를 덮지 않게 한다.
- PC modal과 모바일 bottom sheet는 열릴 때 앱 본문을 `inert`·`aria-hidden`으로 격리하고 닫힐 때 body scroll·배경 속성·실행 버튼 초점을 복원한다. 320px와 200% 확대에서 시간 행·요약·하단 CTA가 잘리지 않는 계약을 유지한다.
- 일반실·특실 행동은 `train_id + seat_class` 복합 identity로 독립 처리한다. 같은 열차의 두 등급을 모두 등록할 수 있고, 좌석 행동을 누르면 별도 확인 단계 없이 해당 열차·등급 작업 하나를 생성·시작해 홈 활동 목록에 바로 반영한다. 상태·행동에는 읽을 수 있는 이름과 의미 색상을 함께 제공하고 선택 상태는 `aria-pressed`, 행동 영역은 최소 44px을 유지한다. 중복 클릭은 pending·success 상태에서 차단하고 실패한 항목만 재시도할 수 있게 한다.
- 새 대기 3단계에는 별도 선택 트레이나 `등록 완료` 버튼을 두지 않는다. 생성 응답의 실제 watch ID를 좌석별 상태에 보존하고, 등록된 같은 좌석 버튼을 다시 누르면 해당 작업을 즉시 취소한다. Home에서 다시 진입하거나 3단계가 remount되어도 활성 DB watch의 `provider + train_number + departure_at` instant + `seat_class`가 현재 좌석과 같으면 active 상태와 실제 watch ID를 hydrate한다. 등록·취소 중에는 그 좌석 버튼만 잠그며 시간표 상태가 바뀌어도 활성 등록의 취소 행동은 유지한다.
- 3단계 상단 원형 새로고침은 명시적 정상 시간표 조회 한 번을 실행한다. 기본 5초 자동 동기화는 마지막 정상 동일 query snapshot을 먼저 읽고, 서버가 60초 이상 지난 cache hit에 한해서만 background revalidation을 단일 작업으로 예약한다. cache miss는 provider로 fallback하지 않는다. 설정 범위는 5~300초이고 관리자 DB에 저장하되 이 값을 상류 호출 주기로 직접 사용하지 않는다. 내용이 같은 열차 객체·배열 참조를 보존하고 memo 카드 경계에서 실제 변경 카드만 렌더링한다. 자동 동기화는 날짜·시간 입력 카드보다 작은 컴팩트 상태 헤더로 표시한다. 원형 아이콘은 빠른 응답에도 최소 한 바퀴(800ms)를 회전하고 느린 응답은 다음 회전 경계에서 정지한다. 고정 폭 `최근 갱신 HH:mm:ss`와 모션 감소 설정을 존중한다.
- `설정 > 화면 동작`은 위 화면 표시 5~300초와 별도로 전역 `좌석 관측 간격` 1~600초를 제공하며 최초 설치 기본값은 5초다. 좌석 관측값은 작업별 모드나 카드별 override 없이 모든 활성 작업에 같은 목표로 적용한다. 설정 UI는 provider cache·운영사별 단일 실행·backoff·circuit·cooldown이 우선해 실제 간격이 길어질 수 있음을 함께 표시하고, 홈 카드에는 폐기된 작업별 속도 선택을 다시 노출하지 않는다.
- 공식 KORAIL·SRT의 `add_to_watch` 등록 행동은 시간표 응답의 유효한 `registration_evidence_id`가 있을 때만 활성화하고, `available`·`limited`·`standing_plus_seat`를 포함한 허용 선택 좌석의 ID를 candidate payload로 전달한다. 공식 예매·예약대기 인계 CTA는 관측 상태에 따라 evidence 없이도 표시할 수 있지만 작업을 생성하지 않는다. API가 실행 provider의 `seat_monitoring=false`를 확인해 `add_to_watch`와 evidence ID를 제거한 경우 상태·provenance는 그대로 표시하고 등록 행동만 fail-closed한다.
- 홈 활동 행은 priority candidate의 immutable `registration_evidence`를 `등록 당시` 상태·출처·관측 시각 감사 정보로만 보존하고, 현재 좌석 상태와 행동은 후보별 `latest_observation`의 status·provenance·`observed_at`·`fresh_until`을 사용한다. 작업 `updated_at`을 좌석 확인 시각으로 쓰지 않으며 migration 이전 candidate는 `등록 근거 없음`으로 구분한다. visible 탭에서는 화면 동작 주기로 `/watches`만 갱신하고 hidden에서는 멈추며 복귀 시 즉시 확인한다. `watch.seat_observed` SSE도 활동 목록을 무효화하며, 활동 목록 헤더의 원형 수동 새로고침과 같은 coordinator를 사용한다. 데이터는 응답 즉시 반영하되 회전 표시는 빠른 응답에도 최소 한 바퀴(800ms)를 유지하고, 느린 응답은 다음 회전 경계에서 자연스럽게 정지한다. 마지막 성공 목록 갱신 시각은 고정폭으로 표시해 주기 갱신 때 레이아웃이 흔들리지 않게 한다. 이 UI는 별도 provider 요청을 만들지 않고 모션 감소 설정과 44px 행동 영역을 지킨다. 최초 REST snapshot은 알림 기준선으로만 사용하고, 이후 감시 중 좌석 발견과 행동 가능 좌석 소실을 각각 상단 큐형 웹 알림으로 한 번만 알린다. `예매` CTA는 현재 후보의 신선한 `available`·`limited`·`standing_plus_seat` 관측이 있을 때만 제공하고, 관측이 사라지거나 매진으로 바뀌면 즉시 제거하되 감시는 출발시각까지 계속한다. CTA는 정확한 잔여 유형을 추정하지 않고 좌석 등급·최근 관측 시각과 공식 최종 확인 안내를 표시한 뒤 기존 `OfficialHandoff`의 여정 복사와 운영사 고정 진입점만 사용한다. 등록 snapshot을 현재 좌석 감시 결과나 예약 성공으로 표현하지 않는다.
- 후보별 최신 예약 시도 outcome·종료 시각·재시도/수동 확인 조건은 toast와 별도로 홈 행에 계속 표시한다. 정책 스위치는 작업 전체에서 단 한 번만 시도한다고 오해되는 표현을 쓰지 않고 `좌석 재발견마다 자동 예매`로 명명한다. 이는 확정적인 비가용 상태 뒤 새 행동 가능 상태가 관측된 새 가용성 에피소드마다 예매를 허용한다는 뜻이며, 같은 에피소드의 중복 호출이나 불명확 결과의 자동 재시도는 뜻하지 않는다. freshness가 끝난 운행·예매창 관측은 `예매창 열림` 같은 현재형 문구를 숨기고 `운행·예매 상태 관측 만료 · 다시 확인 중`으로 강등한다.
- 알림 채널은 단일 관리자 전역 설정이다. 설정되지 않은 Web Push·Telegram·Discord·Webhook 스위치를 켜면 해당 연결·설정 흐름을 시작하고, 설정된 채널은 같은 스위치로 활성·비활성을 바꾼다. 현재 활성 채널은 기존 활동 작업의 다음 알림에도 적용한다. 모바일에서도 설정 행동을 숨기지 않고 44px 영역을 유지하며, Web Push service worker readiness는 bounded timeout으로 실패를 반환하고 무기한 대기하지 않는다. 실제 브라우저 권한 승인과 외부 채널 수신 성공은 운영 smoke test 전까지 완료로 표현하지 않는다. 최초 REST snapshot은 알림 기준선으로만 사용하고 이후 `reserving`, `payment_required`, `auth_required`, 좌석 소실, 예매 실패 후 감시 복귀 전이에 대해 중복되지 않는 상단 toast를 제공한다.
- App 전역의 일반 비차단 알림은 30초, 확인 가능한 진행 단계가 있는 예매 알림은 60초 자동 닫힘과 명시적 닫기 버튼을 사용한다. 결제·인증 행동 알림과 좌석 발견 알림은 자동으로 닫지 않는다. 예약 알림은 운영사·열차번호·날짜·요일·구간·실제 후보 출도착 시각·좌석 등급을 유지하고, 추정한 provider 내부 단계는 표시하지 않는다.
- 접속 중 알림은 좌석 발견과 예매 toast를 별도 고정 레이어로 겹치지 않고 하나의 `실시간 알림` surface에서 관리한다. 같은 watch의 `좌석 발견 → 예매 진행 → 결제·결과 확인`은 새 카드 누적이 아니라 같은 subject의 최신 단계로 교체하며, SSE event·좌석 관측·예약 시도 revision이 같은 알림은 다시 만들지 않는다. 결제·수동 확인·인증·좌석 발견을 진행·복구·일반 알림보다 먼저 표시하고, 동시 다건은 종류별 건수와 펼치기·그룹 닫기를 제공한다. 결제·수동 확인·인증·좌석 발견은 수동 닫기, 예매 진행·복구는 60초, 일반 알림은 30초 계약을 유지한다. surface를 접는 행동은 알림 확인·삭제로 처리하지 않으며 새 알림 도착으로 사용자 초점을 빼앗지 않는다.
- 홈 활동 행은 viewport가 아니라 실제 목록 컨테이너 폭을 기준으로 reflow한다. 좁거나 200% 확대된 화면에서는 운영사·시간, 상태·근거, 정책·행동을 독립 행으로 분리하고 `좌석 재발견마다 자동 예매` label은 줄바꿈하되 switch는 축소하지 않는다. 정책 switch와 pause·cancel은 44px 행동 영역을 유지하고 상태·최근 확인 문구 위에 겹치거나 가로 넘침을 만들지 않는다.
- 설정의 `철도 계정`은 KORAIL·SRT 단일 관리자 credential을 각각 저장·교체·삭제한다. 회원번호·이메일·휴대전화 방식을 명시적으로 선택하고, `로그인 확인 후 저장` 요청이 성공한 뒤에만 편집 화면을 닫는다. 실패 시 방식·ID는 유지하되 비밀번호는 지우며 기존 저장 계정을 교체하지 않는다. 브라우저는 비밀번호를 다시 읽거나 채우지 않고 로그인 방식·마스킹된 아이디·인증 상태만 표시하며, 비밀번호·쿠키·세션·토큰을 URL·toast·로그에 넣지 않는다. 계정 API 404는 원문 `Not Found`가 아니라 실행 서버가 구버전임을 알리는 배포 안내로 표시한다. 연결되지 않거나 비활성·미인증인 운영사가 선택되어 있으면 `reserve_once_before_payment`를 비활성화하고 `notify_only`를 기본으로 한다.
- 새 대기에는 전역 자동화 모드가 아니라 작업별 `좌석 발견 후 행동`을 둔다. 선택한 모든 운영사 계정이 로그인 확인·활성 상태이면 기본값은 `reserve_once_before_payment`이고, 사용자는 언제든 `notify_only`를 선택할 수 있다. 이 정책은 작업 전체 1회가 아니라 좌석 발견 뒤 후보별 DB fence가 허용한 예약 시도를 가용성 에피소드당 최대 한 번 실행하고 `payment_required`에서 멈춘다. 예약 결과나 공식 예약목록에서 보류 없음이 확정된 뒤 확정 비가용→새 행동 가능 관측이 생기면 새 에피소드에서 다시 한 번 시도한다. 같은 에피소드 중복과 `FAILED`·`UNKNOWN`·`PROVIDER_BLOCKED` 등 불명확 결과의 자동 반복, 자동 결제, 결제정보 저장은 제공하지 않는다. 작업을 만든 직후 각 작업에 `startWatch`를 호출하지만 자동 시작 자체를 실행 capability 활성화로 해석하지 않는다.
- KORAIL·SRT 중 한 운영사가 실패해도 다른 운영사의 결과와 선택을 보존하고, 실패한 운영사만 다시 조회할 수 있게 한다.
- 3단계에서도 같은 커스텀 달력으로 실제 출발일을 바꾸거나 시간 범위를 변경해 즉시 다시 조회할 수 있어야 한다. 별도의 요일 재조회 조건처럼 표현하거나 가장 가까운 같은 요일로 자동 이동시키지 않는다. 새 행동은 현재 조회 조건을 사용하되 이미 성공한 등록 snapshot과 홈 작업은 재조회 뒤에도 보존한다.
- 출발역·도착역은 `GET /api/v1/stations`의 `node_id + 역명 + 도시`를 사용한다. 사용자가 텍스트만 직접 입력한 상태에서는 다음 단계로 진행하지 않고 공식 목록 선택을 요구한다. 검색 결과는 정규화한 역명 완전 일치·접두 일치·포함을 지역명 완전 일치·접두 일치·포함보다 먼저 배치하고 빈 검색어에서는 카탈로그 기본 순서를 보존한다. 화면 목록은 TAGO 원본 identity와 KORAIL 공개 역 안내 교집합이지만 운영사별 소속을 보증하지 않으므로 서울 출발 SRT나 수서 출발 KTX를 정적으로 막지 말고 선택 날짜의 시간표 결과로 판단한다.
- 출발역·도착역의 공식 목록 미선택 검증은 사용자가 해당 필드를 건드린 뒤 각 입력 바로 아래에 compact inline 상태로 표시한다. 초기 카탈로그 로드 직후 untouched 필드에는 `aria-invalid`·alert를 노출하지 않고, 실제 다음 단계 차단 검증은 계속 유지한다. 역 교환 버튼은 데스크톱에서 두 combobox control의 수직 중앙, 모바일에서 두 필드 사이의 독립 48px 행동 영역에 둔다.
- 40개 이하 결과는 일반 DOM 목록을 유지한다. 40개 초과 또는 실제 렌더 commit 50ms 초과가 측정되기 전에는 가상화를 도입하지 않으며, 도입 시 선택·포커스 보존과 목록 접근성을 먼저 검증한다.
- 열차 목록은 비교 밀도를 우선한다. 현재 고밀도 기준은 1440px에서 카드 182px이며 320px에서도 가로 넘침 없이 일반실·특실 상태·provenance·CTA와 44px 터치 영역을 유지한다. 정보를 숨겨 더 줄이려면 임의 CSS 축소가 아니라 좌석 상세 접기/펼치기 정보구조를 별도 설계한다.
- 430px 이하 모바일 열차 카드는 데스크톱 2열을 억지로 축소하지 않는다. 운영사·열차번호와 등록 건수, 출도착 시각, 일반실·특실 좌석 패널 순서로 읽히는 티켓형 1열 구조를 사용한다. 활성 등록은 카드의 `대기 등록 N건`, 좌석의 `대기 등록됨`·`좌석 변화를 감시 중`, 진한 위험색 좌석별 `대기 취소` 행동을 함께 표시하고, 재고 상태 색상과 등록 처리 상태 색상을 혼동하지 않는다.
- CAPTCHA·NetFunnel·`-8003`·403 등 공식 보호장치를 우회하거나 비공개 endpoint를 재현하지 않는다. 세부 정책과 공개 감지 신호의 근거 수준은 `docs/POLICY_AND_SAFETY.md`, `docs/research/OFFICIAL_HANDOFF_FALLBACKS.md`, `docs/research/OFFICIAL_AUTOMATION_DETECTION.md`를 따른다.

로컬 서버와 미리보기가 필요하면 이 환경에서 직접 실행하고 사용 가능한 브라우저로 연다. 직접 실행할 수 있는데 사용자에게 서버 시작만 요청하지 않는다.

큰 시각 변경을 하기 전 시각 원본이 불명확하거나 현재 목표와 맞지 않으면 Product Design 플러그인의 `get-context` 스킬을 사용한다. 사용자가 지속적으로 적용할 프로토타입 디자인 피드백·선호·결정을 주면 `AGENTS.md`에 기록한다.

선택된 생성 시안을 구현할 때는 레이아웃, 컴포넌트 구조, 밀도, 간격, 색상, 타이포그래피, 표시 콘텐츠와 위계를 판단하는 시각 원본으로 사용한다.

앱 UI는 `src/`에서 구현한다. 같은 로컬 프로토타입을 Sites로 넘길 수 있도록 `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, `tests/sites-worker.test.mjs`를 유지한다. Sites 인계 전 `npm run build`와 `npm run test:sites`를 실행하고, 빌드 결과에 `dist/client/index.html`, `dist/server/index.js`, `dist/.openai/hosting.json`이 남는지 확인한다.

## TypeScript와 코드 분리

- 신규·수정 React 컴포넌트는 `.tsx`, JSX가 없는 도메인 타입·API·hook·utility는 `.ts`로 작성한다. 기존 `.jsx`·`.js`에 기능을 계속 쌓지 않고 수정하는 책임부터 TypeScript 모듈로 옮긴다.
- 현재 `main.tsx`, strict `App.tsx`와 전체 Vitest TS/TSX 테스트 파이프라인이 적용되어 있다. `api.js`,
  `App.jsx`, legacy JS/JSX 테스트는 제거됐고 `allowJs` 없이 typecheck한다. service worker·Sites worker·
  빌드/ESLint 설정처럼 런타임이 요구하는 `.js`·`.mjs` 경계는 별도 lint·계약 테스트를 유지한다.
- App의 화면·인증·SSE·작업 상태는 `domain types → API mapper → leaf UI → feature hook/page → App shell` 수직 슬라이스로 이미 분리했다. 후속 작업은 `app -> features -> api/domain/shared` 방향과 authentication boundary 위의 controller hook 수명주기, 공개 compatibility export identity를 보존한다.
- 목표 경계는 `app/`, `domain/`, `api/`, `features/`, `shared/ui/`, `shared/lib/`, `fixtures/`이다. 기능 전용 코드는 feature에 함께 두고, 계약이 같은 두 기능 이상에서 사용할 때만 shared로 올린다.
- API DTO, 정규화된 도메인 모델, 화면 ViewModel을 분리하고 외부 JSON은 `unknown`에서 검증한다. 좌석 provenance/status/action과 watch status는 판별 가능한 union으로 표현한다.
- 한 파일 한 책임을 기본으로 하되 단순 줄 수를 맞추려고 작은 표현 컴포넌트를 남발하지 않는다. 독립 상태 흐름, 외부 I/O, 순수 도메인 계산, 재사용 가능한 접근성 UI가 추출 기준이다.
- `any`, `@ts-ignore`, 무근거 `as`, non-null assertion은 사용하지 않는다. 예외가 필요하면 범위를 최소화하고 이유와 회귀 테스트를 남긴다.
- 모든 TypeScript 수직 슬라이스는 `npm run typecheck`, `npm test`, `npm run build`를 통과해야 한다. Sites 경계를 건드리면 `npm run test:sites`도 실행한다.

상세한 단계와 보존할 회귀 계약은 `docs/WEB_TYPESCRIPT_MIGRATION.md`를 따른다.
