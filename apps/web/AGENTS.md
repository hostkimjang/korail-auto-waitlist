# 웹 프로토타입 작업 지침

## 확정된 제품 디자인 방향

- 메인은 정보 밀도가 높은 소비자용 열차 대기 앱 방향을 유지한다.
- 메인은 소비자 앱 형태이며 모든 `payment_required` 작업과 공식 결제 행동을 가장 높은 우선순위로 둔다. 운영사가 timezone-aware `payment_deadline`을 제공한 작업만 실제 남은 시간을 표시하고, 값이 없으면 임의 카운트다운을 만들지 않는다. 복수 결제 작업은 실제 기한 오름차순으로 모두 표시하고 각 작업의 공식 결제 CTA를 유지한다.
- 모바일 PWA와 PC 웹을 같은 정보 구조로 반응형 지원한다. 모바일에서는 결제 카드와 CTA가 첫 화면에 남고, PC에서는 왼쪽 내비게이션과 넓은 작업 영역을 사용한다.
- 시스템 요청 수, worker, cooldown 같은 기술 정보는 홈에 노출하지 않고 `설정 > 로그·진행 상태`로 분리한다. 근거가 없는 서버 오류율이나 worker 상태를 0%·정상으로 추정하지 않고 `기록 없음` 또는 `확인 불가`로 표시하며, 원문 로그·오류 문자열·payload·식별정보는 이 화면에 노출하지 않는다.
- 홈의 활동 중 대기는 고정 개수 제한이나 `slice` 없이 전부 표시한다. 만료·완료·실패 등 비활성 기록은 활동 목록에 섞지 않고 `전체 내역 보기`를 통해 `내 예약`에서 확인한다.
- 현재 구현된 `apps/web/src`의 화면 구조와 디자인 토큰을 시각 기준으로 사용합니다. 경쟁 앱 이름이나 로고는 복제하지 않고 자체 명칭 `레일웨잇`과 자체 앱 아이콘을 사용합니다.
- 브라우저 탭 favicon은 설치용 192·512px 티켓 아이콘을 축소해 쓰지 않는다. 투명한 16·32px 전용 자산에서 네이비 둥근 타일과 흰 체크만 표시하고 HTML `sizes`를 명시한다. Chromium의 favicon·설치 아이콘·서비스 워커 캐시가 이전 픽셀을 유지할 수 있으므로 시각 변경 때는 favicon과 manifest `any` 아이콘에 새 파일 경로를 사용하고 app shell cache 이름도 함께 올린다. 전체 티켓 구성은 PWA `any`·`maskable`과 Apple Touch 자산에 유지한다.
- 온라인 PWA navigation은 network-first로 현재 `index.html`과 같은 배포의 해시 bundle을 사용하고, 네트워크 실패 때만 캐시된 shell로 복구한다. `/assets/`의 없는 이전 해시를 `index.html`로 대체하지 않으며 `index.html`·`sw.js`는 재검증한다. 배포 뒤 구 index와 삭제된 bundle이 섞인 흰 화면을 허용하지 않는다.
- 열차 결과 카드는 시간표·조회 시각·운임·소요시간과 일반실·특실별 상태 패널을 분리해 보여주되 사용자 화면에는 내부 수집원 이름 `TAGO`를 노출하지 않는다. 관측 provenance가 유효할 때만 세부 상태를 `예매 가능`, `매진`, `입석만 가능`, `예약대기 가능`, `예매 불가`로 표시하고, 관측되지 않은 두 등급은 status와 관계없이 `unknown`과 `확인 필요`로 표시한다. SRT 1인 사용자 트리거 조회의 열차번호·날짜·출발시각 exact match는 좌석별 관측값으로 표시하되 다인원·상류 실패·불일치는 `확인 필요`를 유지한다.
- 좌석별 상태 payload는 status만 신뢰하지 않는다. `official_provider`, `user_confirmed_official_page`, `mock` provenance에 source와 `observed_at`이 없거나 계약이 잘못되면 `unknown/not_observed`로 fail-closed하고, mock은 `벤치마크 데모 상태`로 명시한다. 사용자 직접 확인값은 고정 source와 미래의 `fresh_until`이 모두 있어야 하며 `공식 페이지에서 직접 확인`으로 구분한다.
- KORAIL·SRT 열차 단위 `좌석 상태 입력`은 공식 화면을 사용자가 직접 확인한 뒤 명확히 본 일반실·특실 상태만 한 번에 저장한다. 열차 identity와 인원은 수정할 수 없고, 하나 이상의 등급을 선택해야 하며 성공 후 현재 시간표 query만 재조회한다. 입력값을 provider 관측값이나 자동 예약 근거로 표현하지 않는다.
- 일반실·특실은 2열 좌석 패널에서 각각 선택할 수 있게 하고 버튼 이름에 좌석 등급과 행동을 포함한다. 선택 상태는 `aria-pressed`로 전달하며 색상이나 벨·시계 아이콘만으로 상태·행동을 표현하지 않는다.
- 열차 등록 화면은 시간표를 처음 열거나 날짜·시간 범위를 바꿀 때 서버가 일반실·특실 상태를 함께 조회해 자동 반영한다. 브라우저 확장 설치나 별도 가져오기 행동을 요구하지 않으며, 기본 설정 화면에도 레거시 확장 연결·pairing UI를 노출하지 않는다. 미관측·상류 오류일 때만 서버 재조회 버튼을 fallback으로 제공하고, 미관측 좌석은 대기 등록을 막는다. 예매 가능·매진임박·입석+좌석은 공식 예매와, 유효한 evidence 및 실행 `seat_monitoring` capability가 있을 때 선택 좌석별 감시 등록을 함께 제공한다. 순수 입석은 `입석만 가능`으로 표시해 공식 예매 확인과 취소 좌석 감시는 허용하되 좌석 발견·자동 예매 근거로 쓰지 않는다. 매진은 취소표 대기, 예약대기 가능은 공식 예약대기로 구분하며 KORAIL·SRT는 각각의 3중 opt-in에서만 대기 행동을 발급한다. 예약 실행은 별도 1회 gate·로그인 확인된 계정·작업 정책까지 충족할 때만 열린다.
- 공식 채널 인계는 안정적인 공식 HTTPS 링크와 비밀값이 없는 여정 정보 복사로 제공한다. 기본 빌드는 브라우저 탭과 설치형 PWA 모두 예매 단계의 고정 예매 URL, `payment_required`·완료 확인 단계의 고정 예약·승차권 조회 URL을 새 창으로 연다. 순수 PWA에서 package 실행이나 설치 조회가 가능하다고 가정하지 않는다. 코레일+ 7.0.0은 예매에 `korailtalk://navigation?view=booking`, 예약 승차권 조회·취소에 `korailtalk://navigation?view=bookedTicket`을 사용한다. `view=ticket`은 하단 `나의 티켓` 경로이므로 결제 인계에 사용하지 않는다. SRT 2.0.41은 BROWSABLE `srapp://main`을 예매 홈에 사용하고, 같은 진입점에 설치 APK가 명시적으로 읽는 고정 문자열 extra `btnNo=2`를 전달해 승차권 확인으로 이동한다. 다만 SRT ticket 웜 실행은 기존 `SRWebActivity`를 전면에 두기만 하고 승차권 목록을 다시 조회하지 않을 수 있다. `payment_required` SRT 카드에는 방금 예약이 비어 보이면 하단 `승차권 확인`을 다시 누르라는 안내를 노출하고, 공개 refresh 계약 없이 지연된 두 번째 intent·추측 extra·앱 내부 클릭을 자동화하지 않는다. 코레일 booking·ticket과 SRT main·ticket은 각 경로의 ADB resolver·목적 화면·브라우저/PWA 행렬을 통과한 versionName/versionCode가 빌드 설정에 함께 있을 때만 Android 사용자 클릭의 `target="_blank"` anchor intent를 만든다. 설치 앱이 없을 때 고정 HTTPS fallback은 외부 Custom Tab에서 열려 PWA를 보존해야 한다. 사용자·여정·인증 데이터를 intent extra에 넣지 않으며, 목적 화면과 fallback 표시 방식을 모두 만족하지 않으면 해당 경로 플래그를 켜지 않는다. WebView 기반 인앱 브라우저·다른 브라우저·iOS는 HTTPS를 유지하고, provider payload·내부 결제/로그인 scheme·미검증 host를 실행하지 않는다.
- 공식 앱 인계 플래그는 Vite build-time 입력이다. 로컬 QA를 계속할 장비에서는 enabled와 검증 버전을 커밋하지 않는 `.env`에 함께 기록하고, 셸 프로세스에만 설정한 값을 완료 상태로 보지 않는다. 재빌드 전 effective Compose web build args, 재빌드 뒤 배포 번들의 enabled·검증 버전, 새로고침한 일반 Chrome과 standalone PWA의 실제 사용자 클릭을 순서대로 확인한다. 열린 탭의 이전 JavaScript 결과를 새 배포 결과로 기록하지 않는다.
- `OfficialHandoff`는 운영사별 고정 진입점만 열고 provider action URL은 동일 origin·경로 검증 뒤에도 고정 URL로 정규화한다. 선택한 좌석 등급의 provenance만 설명하며, 복사는 명시적인 `true` 반환만 성공으로 보고 `false`·예외·무응답은 모달 안의 읽을 수 있는 실패 요약으로 처리한다. 처리 중에는 중복 복사를 막고, 닫기·재열기 전의 오래된 비동기 결과가 새 dialog 상태를 덮지 않게 한다.
- PC modal과 모바일 bottom sheet는 공통 문서 스크롤 잠금을 사용한다. 첫 modal이 열릴 때 `html`·`body`의 overflow·overscroll과 현재 scroll 좌표를 보존하고 body를 fixed로 고정하며, 중첩 modal이 모두 닫힌 마지막 해제에서만 인라인 스타일과 원래 좌표를 정확히 복원한다. 앱 본문은 `inert`·`aria-hidden`으로 격리하고 실행 버튼 초점을 복원한다. 320px와 200% 확대에서 시간 행·요약·하단 CTA가 잘리지 않는 계약을 유지한다.
- 일반실·특실 행동은 `train_id + seat_class` 복합 identity로 독립 처리한다. 같은 열차의 두 등급을 모두 등록할 수 있고, 좌석 행동을 누르면 별도 확인 단계 없이 해당 열차·등급 작업 하나를 생성·시작해 홈 활동 목록에 바로 반영한다. 상태·행동에는 읽을 수 있는 이름과 의미 색상을 함께 제공하고 선택 상태는 `aria-pressed`, 행동 영역은 최소 44px을 유지한다. 중복 클릭은 pending·success 상태에서 차단하고 실패한 항목만 재시도할 수 있게 한다.
- 새 대기 3단계에는 별도 선택 트레이나 `등록 완료` 버튼을 두지 않는다. 생성 응답의 실제 watch ID를 좌석별 상태에 보존하고, 등록된 같은 좌석 버튼을 다시 누르면 해당 작업을 즉시 취소한다. Home에서 다시 진입하거나 3단계가 remount되어도 활성 DB watch의 `provider + train_number + departure_at` instant + `seat_class`가 현재 좌석과 같으면 active 상태와 실제 watch ID를 hydrate한다. 등록·취소 중에는 그 좌석 버튼만 잠그며 시간표 상태가 바뀌어도 활성 등록의 취소 행동은 유지한다.
- 3단계 상단 원형 새로고침은 명시적 정상 시간표 조회 한 번을 실행한다. 내부 고정 5초 자동 동기화는 마지막 정상 동일 query snapshot을 먼저 읽고, 서버가 60초 이상 지난 cache hit에 한해서만 background revalidation을 단일 작업으로 예약한다. cache miss는 provider로 fallback하지 않는다. 이 내부 복구 주기를 사용자 설정이나 상류 호출 주기로 노출하지 않는다. 내용이 같은 열차 객체·배열 참조를 보존하고 memo 카드 경계에서 실제 변경 카드만 렌더링한다. 자동 동기화는 날짜·시간 입력 카드보다 작은 컴팩트 상태 헤더로 표시한다. 원형 아이콘은 빠른 응답에도 최소 한 바퀴(800ms)를 회전하고 느린 응답은 다음 회전 경계에서 정지한다. 고정 폭 `최근 갱신 HH:mm:ss`와 모션 감소 설정을 존중한다.
- `설정 > 화면 동작`은 화면 표시를 읽기 전용 `실시간` 상태로 설명하고 초 입력을 노출하지 않는다. 중요 상태·예약 이벤트와 Push·수동 갱신은 즉시 canonical 목록 재조회를 요청한다. 반복되는 `watch.seat_observed`는 SSE로 계속 받되 목록 무효화만 다음 내부 고정 5초 복구 조회에 합쳐 canonical GET 시작 간격을 제한한다. 사용자가 조정할 수 있는 값은 전역 `좌석 관측 간격` 1~600초이며 최초 설치 기본값은 5초다. 좌석 관측값은 작업별 모드나 카드별 override 없이 모든 활성 작업에 같은 목표로 적용한다. 설정 UI는 provider cache·운영사별 단일 실행·backoff·circuit·cooldown이 우선해 실제 간격이 길어질 수 있음을 함께 표시하고, 홈 카드에는 폐기된 작업별 속도 선택을 다시 노출하지 않는다.
- 홈 활동 행은 watch별 내부 실행 claim 만료 시각을 사용자 ETA로 표시하지 않는다. 명시적 `observation_execution_state`가 진행 중이면 `좌석 관측 중`, 유휴 상태이면 `다음 좌석 관측 목표`를 표시하며, 백그라운드 관측은 행의 사용자 행동을 잠그거나 `aria-busy`로 표현하지 않는다.
- 공식 KORAIL·SRT의 `add_to_watch` 등록 행동은 시간표 응답의 유효한 `registration_evidence_id`가 있을 때만 활성화하고, `available`·`limited`·`standing_plus_seat`·`standing_only`를 포함한 허용 선택 좌석의 ID를 candidate payload로 전달한다. 공식 예매·예약대기 인계 CTA는 관측 상태에 따라 evidence 없이도 표시할 수 있지만 작업을 생성하지 않는다. API가 실행 provider의 `seat_monitoring=false`를 확인해 `add_to_watch`와 evidence ID를 제거한 경우 상태·provenance는 그대로 표시하고 등록 행동만 fail-closed한다.
- 홈 활동 행은 priority candidate의 immutable `registration_evidence`를 `등록 당시` 상태·출처·관측 시각 감사 정보로만 보존하고, 현재 좌석 상태와 행동은 후보별 `latest_observation`의 status·provenance·`observed_at`·`fresh_until`을 사용한다. 작업 `updated_at`을 좌석 확인 시각으로 쓰지 않으며 migration 이전 candidate는 `등록 근거 없음`으로 구분한다. 홈·새 대기·설정은 `/watches?view=live`로 최근 24시간 안에 바뀐 작업을 상태와 무관하게 읽고, 그보다 오래된 작업은 watch 전체에 exact `CONFIRMED_PAID`가 없으면서 비종단이거나 작업 전체에서 시작시각·sequence·ID 순으로 가장 최신인 예약 시도가 수동 확인을 요구할 때만 읽는다. `내 예약`은 `/watches?view=all`로 전체 이력을 읽는다. 다른 후보의 더 오래된 `UNKNOWN`은 이후 후보의 최신 결제완료·종결 시도를 덮어 terminal watch를 live 목록에 붙잡지 않으며, exact paid 근거가 있는 `PAUSED`·`AUTH_REQUIRED`·`COOLDOWN` 보존 경합도 24시간 뒤에는 live 목록에서 제외한다. 24시간 창으로 놓친 완료·실패 SSE를 복구하고, exact paid가 없으면 창이 지나도 만료된 최신 `UNKNOWN` 등 수동 확인 필요 건은 보존한다. visible 탭에서는 중요 SSE·Push 힌트를 즉시 반영하고, `watch.seat_observed` 무효화는 내부 고정 5초 조회에 합친다. hidden에서는 정기 조회와 이벤트별 lifecycle snapshot 투영을 모두 생략하고 pending 한 건만 남기며 복귀 시 한 번 최신 목록을 읽는다. pause·resume·cancel·정책 변경·기록 삭제 mutation과 교차한 이전 `/watches` 응답은 mutation 응답 snapshot을 덮지 못하며, mutation 종료 뒤 canonical 목록을 다시 읽는다. 기록 삭제 성공 항목은 서버 목록에서 부재가 확인될 때까지 로컬 tombstone으로 유지해 늦은 SSE 무효화가 화면에 되살리지 못하게 한다. 홈 휴지통은 감시 중단을 위한 cancel이고 예약 내역의 삭제만 기록 delete라는 구분을 유지한다. 결제기한 시계와 철도 계정 runtime polling도 hidden 중 멈추고 복귀할 때 즉시 갱신한다. 활동 목록 헤더의 원형 수동 새로고침은 같은 coordinator를 사용한다. 데이터는 응답 즉시 반영하되 회전 표시는 빠른 응답에도 최소 한 바퀴(800ms)를 유지하고, 느린 응답은 다음 회전 경계에서 자연스럽게 정지한다. 마지막 성공 목록 갱신 시각은 고정폭으로 표시해 주기 갱신 때 레이아웃이 흔들리지 않게 한다. 이 UI는 별도 provider 요청을 만들지 않고 모션 감소 설정과 44px 행동 영역을 지킨다. 최초 REST snapshot은 알림 기준선으로만 사용하고, 이후 감시 중 좌석 발견과 행동 가능 좌석 소실을 각각 상단 큐형 웹 알림으로 한 번만 알린다. `예매` CTA는 현재 후보의 신선한 `available`·`limited`·`standing_plus_seat` 관측이 있을 때만 제공하고, 관측이 사라지거나 매진으로 바뀌면 즉시 제거하되 감시는 출발시각까지 계속한다. CTA는 정확한 잔여 유형을 추정하지 않고 좌석 등급·최근 관측 시각과 공식 최종 확인 안내를 표시한 뒤 기존 `OfficialHandoff`의 여정 복사와 운영사 고정 진입점만 사용한다. 등록 snapshot을 현재 좌석 감시 결과나 예약 성공으로 표현하지 않는다.
- 성공한 `/watches?view=live` canonical 응답을 수용한 경우에만 직전 snapshot에서 사라진 watch subject의 sticky 알림을 현재 세션 메모리에서 제거한다. 이 정리로 종단 상태나 예약 결과를 합성하지 않고, 사용자 dismissal로 간주하거나 dismissal ledger에 기록하지 않는다.
- 후보별 최신 예약 시도 outcome·종료 시각·재시도/수동 확인 조건은 toast와 별도로 홈 행에 계속 표시한다. 정책 스위치는 작업 전체에서 단 한 번만 시도한다고 오해되는 표현을 쓰지 않고 `좌석 재발견마다 자동 예매`로 명명한다. 이는 확정적인 비가용 상태 뒤 새 행동 가능 상태가 관측된 새 가용성 에피소드와, `UNKNOWN`의 공식 확인에서 대상 부재를 연속 두 번 확인하고 그보다 새 공식 `available`·`limited` 관측이 생긴 경우의 제한된 1회 복구 episode에서 예매를 허용한다는 뜻이다. 같은 episode의 중복 호출이나 복구 결과의 연쇄 재시도는 뜻하지 않는다. 서버가 `manual_rearm_available`과 닫힌 `manual_rearm_reason`을 함께 확정한 종료 결제보류 또는 세 번 이상 불명확한 `UNKNOWN`에는 확인 dialog가 있는 `자동 예매 다시 시도`를 제공한다. 후보별 최신 attempt 가운데 수동 권한 owner가 정확히 하나이면 watch 전체의 시작시각 최신 attempt보다 그 owner와 candidate context를 행동 문맥으로 우선하고, 둘 이상이거나 context의 candidate/provider가 맞지 않으면 버튼과 dialog를 숨긴다. 모드별 공식 상태 확인란을 선택하기 전에는 제출할 수 없고, 확인 명령은 즉시 일반 관측만 예약하며 승인 뒤 같은 원본 후보의 새 공식 `available`·`limited` 관측에서 한 번만 예매할 수 있다고 설명한다. 다른 후보의 가용성이 watch 전체 `UNKNOWN` fence를 우회하거나 수동 child의 `UNKNOWN`이 재귀 재개되지 않게 한다. 실패하면 dialog를 유지하고, 중복 클릭은 행 단위 pending guard로 막는다.
- 최신 attempt의 `automatic_reservation_retry_fence_reason=confirmed_absent_recovery_consumed`는 공식 부재 확인 뒤 허용된 자동 복구 1회를 이미 사용해 추가 자동 예매가 차단됐다는 닫힌 서버 근거다. raw episode key나 sequence를 웹에서 추정하지 않고 이 값이 있을 때만 소진 문구를 표시한다. 단순 `confirmed_absent`는 대상 예약 없음 확정만 뜻하며 아직 복구 1회가 남았을 수 있다. 두 경우 모두 현재 결과의 수동 공식 확인은 해소된 상태이므로 generic `UNKNOWN` 수동 확인 문구를 표시하지 않고, REST snapshot과 reconciliation SSE가 같은 subject의 이전 sticky 경고를 교체한다.
- `watch.payment_completed` 알림은 닫힌 `payment_required | watching → completed`, `reason=confirmed_paid`, `automatic_reservation_retry=false` 계약을 모두 만족할 때만 완료 toast로 바꾼다. exact paid 근거가 있더라도 canonical watch가 `PAUSED`·`AUTH_REQUIRED`·`COOLDOWN`에 보존된 경합은 `watch.reservation_reconciled`로 목록만 갱신하고 완료 toast를 합성하지 않는다. 이때 exact paid 근거는 수동 재시도와 결제 CTA를 계속 fail-closed한다.
- active pre-reservation의 `scheduled`·`official_waitlist`·`seat_found`·`reserving`에서 exact paid가 확인되면 서버가 먼저 `watching`으로 정규화하고 `completed`로 전이하므로 웹이 받는 canonical 완료 event의 `from`은 계속 `watching`이다. 원래 pre-reservation 상태를 `watch.payment_completed.from` 허용 목록에 직접 추가하지 않는다.
- freshness가 끝난 운행·예매창 관측은 `예매창 열림` 같은 현재형 문구를 즉시 숨긴다. 같은 후보의 동시각 또는 더 최신 정상 좌석 관측, 현재 처리 중인 관측, 미래 또는 30초 grace 안의 다음 목표는 정상 흐름이므로 stale chip을 표시하지 않는다. 활성 감시의 최신 오류·불명확·stale은 운행 projection의 유무나 남은 freshness와 무관하게 원인별 재시도 안내로 우선 표시하고, 미래 cooldown은 재개 목표, 활성 유휴 watch의 30초 초과 overdue는 마지막 성공 상태와 무관하게 응답 지연으로 구분한다. 확정적인 `standing_only`·`sold_out`·`unavailable`·`not_enough_seats`·`not_offered`·`departed`·`out_of_service` 좌석 관측은 scheduler가 정상일 때 비종단 stale projection의 수명을 끝내며, 일시정지·결제·완료·만료 등 비활성 상태에는 보존된 오류·cooldown을 현재 경고로 표시하지 않는다. 운행 취소·출발역 통과·예매 종료·실제 출발시각 같은 종단 사실은 generic 재확인 문구로 덮지 않는다. 홈의 `최근 확인`은 KST `HH:mm:ss`로 표시하되 출도착·좌석 근거 시각은 기존 분 단위를 유지한다.
- 알림 채널은 단일 관리자 전역 설정이다. 설정되지 않은 Web Push·Telegram·Discord·Webhook 스위치를 켜면 해당 연결·설정 흐름을 시작하고, 설정된 채널은 같은 스위치로 활성·비활성을 바꾼다. 현재 기기의 Web Push가 연결되지 않았으면 설정 화면 밖 모든 인증 화면에도 44px 이상 비차단 `OS 알림 켜기` 행동을 유지하고, 그 직접 사용자 행동 안에서 권한 요청부터 구독·서버 저장까지 시작한다. 브라우저가 차단한 권한을 코드로 반복 요청하거나 페이지 로드만으로 승인창을 강제하지 않으며, 사용자가 앱에서 명시적으로 끈 기기에는 전역 연결 행동을 다시 강요하지 않는다. 현재 활성 채널은 기존 활동 작업의 다음 알림에도 적용한다. 모바일에서도 설정 행동을 숨기지 않고 44px 영역을 유지하며, phone과 761~980px compact shell에서는 안내 surface를 하단 탐색 위에 두어 항목을 가리거나 클릭을 가로채지 않는다. Web Push service worker readiness는 bounded timeout으로 실패를 반환하고 무기한 대기하지 않는다. 실제 브라우저 권한 승인과 외부 채널 수신 성공은 운영 smoke test 전까지 완료로 표현하지 않는다. 최초 REST snapshot은 감시·좌석 발견 알림의 기준선으로 사용하되, 이미 `reserving`·`payment_required`·`auth_required`이거나 가장 최근 attempt가 `UNKNOWN` 수동 확인인 canonical 작업은 재접속·remount 때 현재 상태 카드와 저장된 누적 진행 단계로 복원한다. 만료된 `UNKNOWN`도 수동 확인 카드는 복원하되 감시 재개를 주장하지 않는다. 다중 후보에서는 화면 우선순위가 아니라 해당 attempt의 후보 context를 사용한다. 이후 좌석 소실과 예매 결과·감시 복귀 전이도 중복되지 않는 상단 알림으로 제공한다.
- App 전역의 일반 비차단 알림은 30초, 예매 실패·복구 알림은 60초 자동 닫힘과 명시적 닫기 버튼을 사용한다. 현재 `reserving`인 진행 카드와 결제·인증 행동 알림, 좌석 발견 알림은 자동으로 닫지 않고 같은 watch의 다음 canonical revision이나 사용자의 명시적 닫기로 교체·제거한다. 예약 알림은 운영사·열차번호·날짜·요일·구간·실제 후보 출도착 시각·좌석 등급을 유지하고, 추정한 provider 내부 단계는 표시하지 않는다.
- 접속 중 알림은 좌석 발견과 예매 toast를 별도 고정 레이어로 겹치지 않고 하나의 `실시간 알림` surface에서 관리한다. 모바일 상단 종 버튼은 이 surface를 외부에서 펼치며 현재 알림 건수 배지와 알림 없음 상태를 제공한다. 새 revision을 받아들인 순간 Android·Apple 공통 foreground 미리보기를 safe area 아래에 8초간 간략 표시한 뒤 접힌 건수 header로 남기며, `자세히`로만 전체 목록을 펼친다. 8초 경과는 미리보기만 숨기고 sticky notice를 보존하지만, 미리보기의 X와 펼친 카드·그룹의 닫기는 해당 sticky 알림을 실제로 제거한다. 명시적으로 닫은 sticky revision과 subject watermark만 bounded origin-local ledger에 보존해 같은 브라우저의 재접속·remount 뒤 동일하거나 더 오래된 canonical 상태가 되살아나지 않게 하며, 표시만 한 알림과 timed notice는 저장하지 않는다. 같은 subject의 더 최신 revision은 다시 알린다. 같은 watch의 `좌석 발견 → 예매 진행 → 결제·결과 확인`은 새 카드 누적이 아니라 같은 subject의 최신 단계로 교체하며, SSE event·좌석 관측·예약 시도 revision이 같은 알림은 다시 만들지 않는다. status가 같아도 canonical attempt의 진행·수동 확인 revision과 완료된 `NOT_AVAILABLE`·`FAILED` 결과가 바뀌면 반영하고, terminal SSE를 놓쳐도 후보·시작·종료·결과가 일치하는 최신 REST attempt로 진행 카드를 닫는다. SSE 단계 시각은 해당 event payload만 사용하고 미래 REST 관측이나 다른 attempt 시각을 섞지 않으며, 역순·범위 밖 진행 시각은 fail-closed한다. 좌석 발견부터 자동 예매 요청 시작까지의 시간은 같은 후보의 실제 event 시각이 모두 유효할 때만 표시하며 감지 시각이 없으면 0초를 합성하지 않는다. KORAIL provider 내부 단계는 누적 `watch.reservation_progressed` event로 실행 중 같은 sticky 카드에 확인된 단계만 추가하고, 아직 발생하지 않은 단계나 완료시간을 추정하지 않는다. 후보 context가 이미 있으면 진행 event를 `/watches` 전체 재조회 없이 반영하고, 초기·오래된 snapshot이라 매핑할 수 없으면 event를 queue에 보존해 한 번 갱신한 뒤 재투영한다. 최종 `watch.reservation_result`는 authoritative superset이며 같은 시각의 진행 event보다 우선한다. KORAIL 공식 확인 재투영은 원래 progress를 보존하며, 결과 카드에는 `감지 후`, `이전 단계 후`, `전체`를 구분해 검색 결과·열차 재확인과 예약 클릭 이후 구간을 비교할 수 있게 한다. 활성 단계 spinner는 상태가 바뀔 때까지 반복하되 reduced-motion에서는 애니메이션을 끈다. 완료되지 않은 reserving 상태에는 전체 시간을 합성하지 않는다. 결제·수동 확인·인증·좌석 발견을 진행·복구·일반 알림보다 먼저 표시하고, 동시 다건은 종류별 건수와 펼치기·그룹 닫기를 제공한다. 접힌 상태에서는 벨·건수 header·짧은 peek만 마운트하고 상세 group과 `AppToast` DOM은 사용자가 펼친 동안에만 마운트한다. 미리보기·접힘·펼침 상태 모두 페이지 스크롤·탐색·입력을 잠그지 않는 비차단 UI로 유지하며, 공통 문서 스크롤 잠금은 `aria-modal`인 실제 dialog에만 적용한다. 달력은 알림보다 위, 공식 인계·좌석 입력·역 선택 dialog보다 아래에 쌓는다. 결제·수동 확인·인증·좌석 발견·현재 예매 진행은 수동 닫기, 복구는 60초, 일반 알림은 30초 계약을 유지한다. 새 알림 도착으로 사용자 초점을 빼앗거나 두 번째 live region을 만들지 않는다.
- KORAIL progress의 내부 `seat_selected` 단계는 호차·좌석번호 선택이 아니라 요청한 일반실·특실 운임 control 선택이다. 화면에는 반드시 `객실 등급 선택`으로 표시하고 물리 좌석을 골랐다고 표현하지 않는다. 실제 호차·좌석번호는 KORAIL이 자동 배정하며 공식 결과에서 둘 다 확인된 값만 기존 예약 좌석 UI에 표시한다.
- KORAIL attempt의 누적 progress가 비어 있고 공식 확인 근거도 없는 `FAILED/provider_unavailable`은 예약 요청 전 철도사 연결 준비 실패다. `예약 요청`·`공식 결과 확인` 단계를 합성하거나 공식 예약 내역 확인을 요구하지 않는다. 저장된 `reservation_requested` 또는 결과 불명 근거가 있는 `UNKNOWN`만 예약 명령 뒤 수동 확인 경로로 표시한다.
- KORAIL·SRT 외부 adapter 호출 자체에서 timeout·transport·응답 검증 예외가 탈출하면 예약 명령 전달 전 실패라고 추정하지 않는다. 서버가 보존한 `UNKNOWN`과 실제 progress·confirmation 근거만 표시하고, progress가 없으면 `예약 요청` 단계를 완료로 합성하지 않는다.
- Web Push는 같은 watch를 안정적인 notification tag로 갱신하고, 기본 클릭에서 외부 공식 URL을 열지 않는다. `notificationclick`은 동일 출처의 기존 PWA client를 message한 뒤 focus를 시도하고, focus 결과가 제한 시간 안에 visible로 확인되지 않으면 같은 client를 PWA scope 내부 URL로 navigate한 뒤 다시 focus한다. navigate가 성공했어도 재초점 결과가 visible이 아니면 성공으로 간주하지 않고, focus·navigate 실패나 client 부재와 함께 `openWindow`로 PWA scope 내부 URL을 연다. manifest `launch_handler.client_mode`는 백그라운드 PWA 복귀 회귀를 피하기 위해 `navigate-existing`을 유지한다. 접속 중 Push message는 비밀값 없는 힌트로만 사용하며, 화면은 기존 REST/SSE 경계에서 canonical watch를 재조회한 뒤 알림 센터의 subject·revision 중복 제거를 적용한다. 시간 민감 상태와 정확한 테스트 envelope에만 `Urgency: high`를 붙이고 `reserving`은 좌석 발견의 긴급 tag 갱신을 유지한다. iOS·iPadOS Web Push 연결은 16.4 이상 홈 화면 설치 PWA와 기능 감지를 기준으로 하며, 권한 요청을 사용자 클릭 직후 네트워크 await보다 먼저 실행한다. Android heads-up과 Apple banner·Focus는 OS와 사용자 설정에 좌우되므로 보장 표현을 사용하지 않는다.
- 홈 활동 행은 viewport가 아니라 실제 목록 컨테이너 폭을 기준으로 reflow한다. 좁거나 200% 확대된 화면에서는 운영사·시간, 상태·근거, 정책·행동을 독립 행으로 분리하고 `좌석 재발견마다 자동 예매` label은 줄바꿈하되 switch는 축소하지 않는다. 정책 switch와 pause·cancel은 44px 행동 영역을 유지하고 상태·최근 확인 문구 위에 겹치거나 가로 넘침을 만들지 않는다.
- 설정의 `철도 계정`은 KORAIL·SRT 단일 관리자 credential을 각각 저장·교체·삭제한다. 회원번호·이메일·휴대전화 방식을 명시적으로 선택하고, `로그인 확인 후 저장` 요청이 성공한 뒤에만 편집 화면을 닫는다. 실패 시 방식·ID는 유지하되 비밀번호는 지우며 기존 저장 계정을 교체하지 않는다. 브라우저는 비밀번호를 다시 읽거나 채우지 않고 로그인 방식·마스킹된 아이디·인증 상태만 표시하며, 비밀번호·쿠키·세션·토큰을 URL·toast·로그에 넣지 않는다. 계정 API 404는 원문 `Not Found`가 아니라 실행 서버가 구버전임을 알리는 배포 안내로 표시한다. 연결되지 않거나 비활성·미인증인 운영사가 선택되어 있으면 `reserve_once_before_payment`를 비활성화하고 `notify_only`를 기본으로 한다. canonical watch가 `auth_required`이거나 최신 `UNKNOWN` reconciliation이 `auth_required`·`provider_blocked`이면 늦게 도착한 계정 `authenticated` snapshot보다 이 중단 근거를 우선해 로그인 확인 안내를 표시하고, 해당 reconciliation SSE를 일반 수동 확인 알림으로 강등하지 않는다.
- 새 대기에는 전역 자동화 모드가 아니라 작업별 `좌석 발견 후 행동`을 둔다. 선택한 모든 운영사 계정이 로그인 확인·활성 상태이면 기본값은 `reserve_once_before_payment`이고, 사용자는 언제든 `notify_only`를 선택할 수 있다. 이 정책은 작업 전체 1회가 아니라 좌석 발견 뒤 후보별 DB fence가 허용한 예약 시도를 가용성 에피소드당 최대 한 번 실행하고 `payment_required`에서 멈춘다. 예약 결과나 공식 예약목록에서 보류 없음이 확정된 뒤 확정 비가용→새 행동 가능 관측이 생기면 새 에피소드에서 다시 한 번 시도한다. `UNKNOWN`은 연속 두 번의 공식 부재 확인 뒤 새 공식 `available`·`limited` 관측이 생긴 경우 자동으로 한 번 복구한다. 공식 확인이 세 번 이상 불명확하면 정확한 공식 예약 부재를 사용자가 확인한 승인 뒤의 새 공식 `available`·`limited` 관측에서만 한 번 수동 복구한다. 같은 episode 중복, 두 복구 시도의 재귀 반복, `FAILED`·`PROVIDER_BLOCKED`의 자동 반복, 자동 결제, 결제정보 저장은 제공하지 않는다. 작업을 만든 직후 각 작업에 `startWatch`를 호출하지만 자동 시작 자체를 실행 capability 활성화로 해석하지 않는다.
- `confirmation_correlation_seats`는 결과 불명 시도를 공식 기록과 연결하기 위한 서버 전용 비공개 근거다. REST·SSE·outbox·웹 domain type에 추가하거나 `reserved_seats`로 추정하지 않는다. 서버가 SRT의 exact 공식 미결제 보류를 확인해 확정 `reserved_seats`로 승격한 뒤에만 기존 예약 좌석 UI를 사용하며, KORAIL `UNKNOWN_RESULT_FOLLOW_UP`은 exact 발권 완료만 허용하므로 미결제 목록에서 좌석을 합성하지 않는다.
- KORAIL·SRT 중 한 운영사가 실패해도 다른 운영사의 결과와 선택을 보존하고, 실패한 운영사만 다시 조회할 수 있게 한다.
- 3단계에서도 같은 커스텀 달력으로 실제 출발일을 바꾸거나 시간 범위를 변경해 즉시 다시 조회할 수 있어야 한다. 별도의 요일 재조회 조건처럼 표현하거나 가장 가까운 같은 요일로 자동 이동시키지 않는다. 새 행동은 현재 조회 조건을 사용하되 이미 성공한 등록 snapshot과 홈 작업은 재조회 뒤에도 보존한다. 시간 프리셋은 새벽 `00:00–09:00`, 저녁 `18:00–00:00`으로 표시하고, 다음 자정을 같은 날짜의 `00:00`으로 보내 범위를 뒤집지 말고 기존 서비스 날짜 종료 sentinel `23:59`로 전달한다. 선택 열차가 자정을 넘어 도착하면 후보의 aware `arrival_at`은 익일 시각 그대로 보존하되, 단일 서비스 날짜인 watch window의 `time_to`는 `23:59:59`로 닫아 23시대 출발을 API가 역전 범위로 거절하지 않게 한다.
- 앱 셸은 접속 경로를 확인하지 않은 채 `Tailscale 보호됨` 같은 보안 상태를 단정하지 않는다. Tailscale Serve·Funnel·일반 HTTPS·loopback은 브라우저 hostname만으로 신뢰성 있게 구분할 수 없으므로, 검증된 서버 access-context 계약이 생기기 전에는 정적 보호 배지를 표시하지 않는다.
- 출발역·도착역은 `GET /api/v1/stations`의 `node_id + 역명 + 도시`를 사용한다. 사용자가 텍스트만 직접 입력한 상태에서는 다음 단계로 진행하지 않고 공식 목록 선택을 요구한다. 검색 결과는 정규화한 역명 완전 일치·접두 일치·포함을 지역명 완전 일치·접두 일치·포함보다 먼저 배치하고 빈 검색어에서는 카탈로그 기본 순서를 보존한다. 화면 목록은 TAGO 원본 identity와 KORAIL 공개 역 안내 교집합이지만 운영사별 소속을 보증하지 않으므로 서울 출발 SRT나 수서 출발 KTX를 정적으로 막지 말고 선택 날짜의 시간표 결과로 판단한다.
- 모바일·coarse pointer 태블릿은 출발역·도착역을 한 full-screen route dialog에서 연속 선택한다. 검색 전에는 주요 역·지역 탐색을 제공하고 출발역 선택 뒤 도착역으로 이동한다. 상단 여정 슬롯과 검색창은 가상 키보드가 열린 실제 `visualViewport.height`·`offsetTop` 안에 남기고 결과 영역만 스크롤하며, `100dvh`만으로 키보드 회피를 가정하지 않는다. dialog는 portal, `aria-modal`, 앱 본문 `inert`·`aria-hidden`, 공통 문서 스크롤 잠금, focus trap·복원, Escape와 IME composition Enter 보호를 유지한다. 320px·200% 확대·모바일 세로 키보드·태블릿 가로/분할 키보드에서 44px 이상 행동 영역과 가로 넘침이 없는지 확인한다.
- 출발역·도착역의 공식 목록 미선택 검증은 사용자가 해당 필드를 건드린 뒤 각 입력 바로 아래에 compact inline 상태로 표시한다. 초기 카탈로그 로드 직후 untouched 필드에는 `aria-invalid`·alert를 노출하지 않고, 실제 다음 단계 차단 검증은 계속 유지한다. 역 교환 버튼은 데스크톱에서 두 combobox control의 수직 중앙, 모바일에서 두 필드 사이의 독립 48px 행동 영역에 둔다.
- 40개 이하 결과는 일반 DOM 목록을 유지한다. 40개 초과 또는 실제 렌더 commit 50ms 초과가 측정되기 전에는 가상화를 도입하지 않으며, 도입 시 선택·포커스 보존과 목록 접근성을 먼저 검증한다.
- 열차 목록은 비교 밀도를 우선한다. 현재 고밀도 기준은 1440px에서 카드 182px이며 320px에서도 가로 넘침 없이 일반실·특실 상태·provenance·CTA와 44px 터치 영역을 유지한다. 정보를 숨겨 더 줄이려면 임의 CSS 축소가 아니라 좌석 상세 접기/펼치기 정보구조를 별도 설계한다.
- 430px 이하 모바일 열차 카드는 데스크톱 2열을 억지로 축소하지 않는다. 운영사·열차번호와 등록 건수, 출도착 시각, 일반실·특실 좌석 패널 순서로 읽히는 티켓형 1열 구조를 사용한다. 활성 등록은 카드의 `대기 등록 N건`, 좌석의 `대기 등록됨`·`좌석 변화를 감시 중`, 진한 위험색 좌석별 `대기 취소` 행동을 함께 표시하고, 재고 상태 색상과 등록 처리 상태 색상을 혼동하지 않는다.
- CAPTCHA·NetFunnel·`-8003`·403 등 공식 보호장치를 우회하거나 비공개 endpoint를 재현하지 않습니다. 세부 원칙은 `docs/POLICY_AND_SAFETY.md`를 따릅니다.

로컬 서버와 미리보기가 필요하면 이 환경에서 직접 실행하고 사용 가능한 브라우저로 연다. 직접 실행할 수 있는데 사용자에게 서버 시작만 요청하지 않는다.

큰 시각 변경을 하기 전 시각 원본이 불명확하거나 현재 목표와 맞지 않으면 Product Design 플러그인의 `get-context` 스킬을 사용한다. 사용자가 지속적으로 적용할 프로토타입 디자인 피드백·선호·결정을 주면 `AGENTS.md`에 기록한다.

선택된 생성 시안을 구현할 때는 레이아웃, 컴포넌트 구조, 밀도, 간격, 색상, 타이포그래피, 표시 콘텐츠와 위계를 판단하는 시각 원본으로 사용한다.

앱 UI는 `src/`에서 구현한다. 같은 로컬 프로토타입을 Sites로 넘길 수 있도록 `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs`, `tests/sites-worker.test.mjs`를 유지한다. Sites 인계 전 `npm run build`와 `npm run test:sites`를 실행하고, 빌드 결과에 `dist/client/index.html`, `dist/server/index.js`, `dist/.openai/hosting.json`이 남는지 확인한다.

## TypeScript와 코드 분리

- 신규·수정 React 컴포넌트는 `.tsx`, JSX가 없는 도메인 타입·API·hook·utility는 `.ts`로 작성한다. 기존 `.jsx`·`.js`에 기능을 계속 쌓지 않고 수정하는 책임부터 TypeScript 모듈로 옮긴다.
- 현재 `main.tsx`, strict `App.tsx`와 전체 Vitest TS/TSX 테스트 파이프라인이 적용되어 있다. `api.js`,
  `App.jsx`, legacy JS/JSX 테스트는 제거됐고 `allowJs` 없이 typecheck한다. service worker·Sites worker·
  빌드/ESLint 설정처럼 런타임이 요구하는 `.js`·`.mjs` 경계는 별도 lint·계약 테스트를 유지한다.
- App의 화면·인증·SSE·작업 상태는 `domain types → API mapper → leaf UI → feature hook/page → App shell` 수직 슬라이스로 이미 분리했다. 후속 작업은 `app -> features -> api/domain/shared` 방향과 authentication boundary 위의 controller hook 수명주기, 공개 compatibility export identity를 보존한다.
- 목표 경계는 `app/`, `domain/`, `api/`, `features/`, `shared/ui/`, `shared/lib/`, `fixtures/`이다. 기능 전용 코드는 feature에 함께 두고, 계약이 같은 두 기능 이상에서 사용할 때만 shared로 올린다.
- API DTO, 정규화된 도메인 모델, 화면 ViewModel을 분리하고 외부 JSON은 `unknown`에서 검증한다. 좌석 provenance/status/action과 watch status는 판별 가능한 union으로 표현한다.
- 한 파일 한 책임을 기본으로 하되 단순 줄 수를 맞추려고 작은 표현 컴포넌트를 남발하지 않는다. 독립 상태 흐름, 외부 I/O, 순수 도메인 계산, 재사용 가능한 접근성 UI가 추출 기준이다.
- `any`, `@ts-ignore`, 무근거 `as`, non-null assertion은 사용하지 않는다. 예외가 필요하면 범위를 최소화하고 이유와 회귀 테스트를 남긴다.
- 모든 TypeScript 수직 슬라이스는 `npm run typecheck`, `npm test`, `npm run build`를 통과해야 한다. Sites 경계를 건드리면 `npm run test:sites`도 실행한다.

상세한 단계와 보존할 회귀 계약은 `docs/WEB_TYPESCRIPT_MIGRATION.md`를 따른다.
