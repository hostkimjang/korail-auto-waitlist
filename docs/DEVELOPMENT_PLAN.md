# 최근 이슈 분석과 개발 진행 계획

기능 분석과 운영 배포 상태는 2026년 10월 16일 KST에 다시 확인했습니다. 최근 작업 채팅, 장애 기록, 현재 코드와 운영 서버의
읽기 전용 상태를 함께 대조했습니다. 세부 실험 이력은 [운영 장애 기록](INCIDENTS.md)에 남기고,
이 문서에는 현재 결론과 다음 재개 조건을 정리합니다.

## 2026년 11월 1일 로컬 재점검과 우선 과제

로컬 KORAIL 자동 인증은 12:11 KST에 성공했지만 12:34에 공식 화면의 `미허가 도구` 보호 표식을
감지해 상주 세션이 `blocked`·재사용 불가가 됐습니다. 저장된 마지막 인증 성공은 과거 이력으로 남아
있으며 현재 세션 성공을 뜻하지 않습니다. 서비스 health와 활성 감시 0건도 자동 관측의 성공 근거가 아닙니다.

13:00에 공통 대기 만료만 확인하고 서울→부산 공개 좌석 조회를 한 차례 실행해 공식 출처 16편을
받았습니다. 그러나 인증 복구 전 같은 운영사의 좌석 관측을 중단하는 안전 원칙과 충돌한 실행이었습니다.
이 양성 표본을 인증이나 지속적인 감시 복구로 해석하지 않으며 추가 공식 요청을 중단합니다.

코드 대조에서 인증 예열의 실제 보호 판정은 API 프로세스 메모리에만 남고 계정의 마지막 성공 이력은
유지되는 반면, 감시 worker는 DB의 `provider_blocked`만 확인하는 빈틈을 발견했습니다. 같은 날 이 빈틈을
닫는 구현을 반영했습니다. 정지 사실은 계정 행의 별도 컬럼 쌍(정지된 credential generation과 정지 당시
revision의 micros)으로 저장되며, 현재 행의 revision과 정확히 일치할 때만 유효한 compare-and-swap입니다.
keepalive가 보호 응답을 받으면 정지를 저장하고, 재시작 후 최초 예열은 저장된 정지를 복원해 같은
revision에 로그인을 다시 쓰지 않습니다. 관측 worker도 같은 정지를 읽어 인증 이력이 `authenticated`로
남아 있어도 좌석 조회 대기를 유지합니다. 재사용 가능한 공식 양성 세션이 확인되면 정지 제거와 watch
재개가 같은 트랜잭션으로 커밋되고, 어떤 인증 쓰기든 행 revision을 회전시키면 정지가 자동 만료되며,
새 자격 증명 저장은 무정지 상태로 시작합니다. 정지 저장 실패는 프로세스 내 정지만 유지하는
fail-closed이며, 계정 삭제 후 재등록은 새 행이라 처음부터 무정지입니다. 인증 상태의 의미·재시도
예산과 로그인 성공 이력은 바꾸지 않았고, 같은 값을 재저장하거나 재시작해 차단을 우회하지 않습니다.

같은 날 후속 조정으로 조회 제한 대기를 크게 줄였습니다. KORAIL 공통 대기는 보호 응답에 900초 하한 대신
`SEAT_STATUS_PROTECTION_COOLDOWN_SECONDS`(기본 60초)를, 호출 제한에 `SEAT_STATUS_RATE_LIMIT_COOLDOWN_SECONDS`
(기본 300초)를 씁니다. 계정 보호 정지도 사람이 다시 확인할 때까지 멈추지 않고, 같은 revision에서 60초부터
최대 300초까지 늘어나는 간격으로 자동 재로그인합니다. 정지의 DB 저장과 재시작 직후 즉시 로그인 금지는
그대로이며, 재시도가 성공하면 기존 경로대로 정지가 풀리고 감시가 재개됩니다. 보호가 계속되는 동안에는
시간당 최대 십여 회의 로그인이 생길 수 있으므로 실제 계정 영향은 운영 확인 항목으로 남깁니다.

SRT는 공식 원시 응답의 미지원 열차 코드가 라이브러리 분류에서 빠져 0편으로 반환된 표본이 있습니다.
빈 배열만으로 실제 운행 없음과 분류 누락을 구별할 수 없어, 같은 날 시간표와 서버 좌석 패널의 운행 없음
단정을 "확인되지 않음" 안내로 완화하고 공식 앱·홈페이지 확인을 함께 안내하는 문구를 반영했습니다(v1.2.15).
미지원 코드 `0A`의 제공원 이관·종료는 출처와 예약 경로를 함께 정하는 별도 정책이며 미지원 코드를
임의로 매핑하지 않습니다.

별도로 시간 carousel의 드래그 중 반복 취소가 들어오면 mouse release 완료 전에 상위 작업이 종료되는
결함을 오프라인에서 재현했습니다. 같은 날 release를 shield로 취소 유실을 막으면서 2초 유예시간을 둬,
브라우저 연결이 멈추면 무기한 대기 대신 `departure_hour_navigate` fail-closed 신호로 전환되도록 수정했습니다.
이 신호는 검색 actor의 기존 세션 폐기 경로와 연결돼 멈춘 페이지를 재사용하지 않으며, 유예시간 경계를
회귀 테스트로 확인했습니다.

## 10월 16일 배포 상태

최신 로컬 작업 트리를 Oracle에 반영하고 두 환경의 전체 프로필 재빌드·재생성·health와 실제 설치 소스
일치를 확인했습니다. 기존 HTTPS 주소의 502도 해소돼 Chrome에서 관리자 로그인 화면이 열립니다.
초기 검증 뒤 로컬은 중지했으나, 후속 요청으로 v1.2.14 전체 프로필을 다시 빌드·재생성해 현재는 실행
중입니다. 데이터와 volume은 보존했고, 비교 중 잠시 멈춘 작업자 다섯 개도 모두 재개했습니다.

10월 11일의 로컬 인증 성공을 현재 Oracle 인증 성공으로 확대하지 않습니다. Oracle의 현재 KORAIL
계정 세대 4는 `blocked`·재사용 불가이며, 공식 인증·좌석 조회·예약 복구는 남아 있습니다.
세부 근거와 검증 결과는 [최신 배포 장애 기록](INCIDENTS.md#2026년-10월-16일--oracle-최신-배포와-https-502-복구)을 참고하세요.

사용자가 보고한 `조회 제한`도 현재 서버에서 확인했습니다. 14:12:32 KST 로그인 응답은 `protection`이었고
그 결과 로그인·검색 공통 대기가 열렸습니다. 열차 목록은 TAGO fallback으로 표시할 수 있으나 공식 좌석
상태는 확인되지 않은 상태입니다. 공통 대기를 누락해 `ready`를 반환하던 상태 API를 수정했고, 실제 좌석
조회 복구도 대기 자연 만료 뒤의 공식 읽기로 검증했습니다. 14:27:33 KST에 시작한 서울→부산
10월 17일 조회는 약 31초 뒤 `source_unavailable/wait_result`·HTTP 503으로 실패했습니다. 같은 시간대
자동 로그인도 다시 보호 응답을 받아 공통 대기가 열렸으므로, 현재 운영 서버의 좌석 조회는 미복구입니다.

후속 진단에서는 자동 로그인과 읽기 조회가 겹치지 않도록 API를 잠시 중지하고, 기존 공통 대기의 자연
만료를 기다려 정상 검색 폼의 역·날짜·시간 선택과 단회 제출까지 확인했습니다. 15:16~15:17 KST 표본도
결과 행 0건과 HTTP 200 JSON의 정확한 `errCode=macro_err1`로 끝났습니다. 결과 URL shortcut만 제거하면
복구된다는 가설은 이 표본에서 지지되지 않았습니다. API의 재사용 가능한 인증 세션도 없으므로 과거 로그인
성공을 검색 성공으로 투영하지 않습니다. 보호 응답을 놓치는 판독과 같은 revision의 반복 자동 로그인은
코드에서 수정하되, 실제 공식 좌석 수집 완료 항목은 계속 미완료로 둡니다.

## 현재 결론

17시대 로컬 후속 수정으로 공식 예약 목록 완료 이벤트의 시각 역전을 잘못 거부하던 원인을 고쳤고,
전체 프로필 재생성·설치 소스 일치 뒤 346편을 공식 연속 부재로 해소했습니다. 현재 남은 348편은 해당
시도의 새 배정 좌석 상관 정보가 없어 공식 근거 부족입니다. 화면과 로그로 원인을 분리했고, 근거 없이
부재를 확정하거나 재예약하지 않습니다. 이 후속 수정은 로컬에만 반영했으며 아래 동일 소스 비교는
앞선 16시대 시점의 기록입니다.

집컴도 v1.2.14로 최신화했고 장기 서비스 12개 healthy, 초기화 종료 0, 스키마 0041을 확인했습니다.
16시대 로컬과 Oracle의 API·KORAIL adapter 설치 파일은 각각 301개 모두 당시 소스와 일치했습니다. 로컬의
실제 새 대기 조회에서 47편·좌석 등급 94개의 공식 예매 가능·매진임박·매진·입석+좌석을 받았습니다.
사용자 화면 표본이나 TAGO 시간표를 좌석 수집으로 간주한 것이 아닙니다. 두 환경에 같은 순간 새 조회를
제출한 실험은 아니지만, 최신 소스에서 로컬 양성·Oracle 공식 네트워크 제한을 구분할 근거가 확보됐습니다.

16시대 비교에서 잠시 멈춘 작업자 재개 뒤 오늘 대기 6건의 공식 관측이 16:47~16:48 KST까지 갱신됐습니다. 오래된 날짜의
비종단 대기·5분 초과 진행 중 예약·활성 대기의 만료된 관측 잠금·실제 발송 대기는 0건입니다. 과거 DB를
초기화하지 않았고 `watch.*` outbox·lease fence도 보존했습니다. 322편의 결과 불명은 공식 연속 부재로
해소됐으나 당시에는 346편의 공식 내역 읽기 실패가 남았습니다. 재개된 사용자 자동 예매에서 오늘 348편
일반실도 결과 불명이 생겨 16:53 KST 기준 최근 미해소는 두 건이었습니다. 17시대 수정 뒤에는 위와 같이
346편을 해소하고 348편만 공식 근거 부족으로 유지합니다. 화면에서 경고를 지우거나 예약 성공을 만들어
해결하지 않습니다. 최신 근거는 [장애 기록](INCIDENTS.md)에 모았습니다.

16:02 KST에는 운영 컨테이너의 실제 Chrome 화면을 캡처해, 빈 결과 위에 표시된 공식 안내
`VPN 또는 데이터센터를 통해서는 서비스를 이용할 수 없습니다. CODE: -8202`를 확인했습니다.
따라서 현재 직접적인 중단 이유는 공식 네트워크 제한이며, 단순 좌석 파싱이나 로그인 입력 실패로
설명하지 않습니다. proxy 환경변수와 Tailscale exit node는 없었고, 핵심 JavaScript 자산도 브라우저에서
로드를 완료했습니다. Oracle 서버 회선의 데이터센터 분류와 부합하지만 운영사의 세부 판정 기준은
확인하지 않았습니다. 다음 실제 수집 검증은 현재 서버의 접근 허용 또는 별도로 허용된 연동 경로가
확인된 뒤 진행해야 합니다. IP·프록시·브라우저 교체로 이 제한을 피하는 실험은 하지 않습니다.

공식 페이지의 익명 좌석 조회에는 별도 제휴 API나 로그인 성공을 선행 조건으로 두지 않습니다. 사용자의
정상 Chrome은 로그인 전에도 실제 결과 60행을 표시했고, 그중 3행은 현재 production 파서에서
매진·매진임박·예매 가능으로 정상 변환됐습니다. 현재 남은 문제는 서버 브라우저가 이 정상 응답·DOM을
확보하지 못하는 경계이며, 정상 페이지가 보이는 사실만으로 서버 자동 수집을 복구 완료로 올리지 않습니다.
동일 조건을 운영 sidecar에서 대조한 15:47:06 KST 조회도 5.71초 뒤 HTTP 423·`marker_macro_err1`·0행으로
끝났습니다. 따라서 현재 완료 조건은 충족하지 못했으며, 보호 응답을 무시하거나 사용자 화면 표본을 서버
관측값으로 합성해 완료 처리하지 않습니다.

설정 화면의 상주 세션 최신성 문제는 해결했습니다. 런타임 조회 상태를
`idle | loading | ready | unavailable`로 분리했고, 가장 최근의 활성 요청만 화면에 반영합니다.
조회 실패, 로그아웃, 화면 종료, polling 중단, 계정 저장·교체·삭제 뒤 늦게 도착한 응답은 무효화합니다.
저장 계정의 `credentialVersion`과 런타임의 `credentialGeneration`이 같은 경우에만 `재사용 가능`으로
표시합니다. 이 변경은 화면의 잘못된 현재 상태를 바로잡는 것이며, 기존 백엔드의 동일 세대 예약 fence는
완화하지 않았습니다.

KORAIL 로그인 실패의 현재 경계도 확인했습니다. 공개 번들의 실제 로그인 호출 위치를 검증한 뒤,
비밀값을 남기지 않는 진단을 배포하고 17:25 KST에 로그인 사전 점검을 한 번만 실행했습니다. 공개 키 요청은
HTTP 200으로 끝났고, 실제 로그인 제출 호출은 HTTP 200 JSON 응답의 `errCode=macro_err1`으로 종료됐습니다.
제품은 이를 인증 실패나 일반 서버 오류가 아닌 `provider_access_restricted` 보호 응답으로 분류하고 공유
Redis에 최소 900초 대기를 열었습니다. 17:26 KST 감사 때 남은 대기는 804초였습니다.

같은 날 20:28·20:34 KST에는 같은 서버·adapter 이미지·Xvfb·headed Google Chrome 151을 유지하고
컨트롤러만 Playwright로 바꿔 5분 이상 간격의 제한 비교를 두 번 수행했습니다. 두 번 모두 입력 일치와
UI 클릭 1회씩은 확인했지만 인증은 0회였습니다. 두 번째 실행에서 같은 출처 공식 POST 1건이 2xx로
끝났으나 exact 로그인 경로는 아니었고 닫힌 분류는 `other`였습니다. DynaPath가 논리 경로를 실제 네트워크

## 로그인 제출과 보호 응답 분석

공개 번들 `/bundle/bundle.fcfd32491c1f6e0b2541.js?v=1.0.221`은 5,849,655바이트이며 SHA-256은
`8a9519dd552db96a7f30bf9f1ceb0b8eae7da0b5c17702b07e1e1650bebdc72b`입니다. 이 파일에서
`handleLogin`이 공개 키를 받은 뒤 입력을 암호화하고 `callApi(API.LOGIN, payload)`를 호출하는 흐름과,
`API.LOGIN`이 `POST /ebizweb/common/loginProcess`인 것을 확인했습니다. 번들 자체도 `macro_err1`을
별도 오류로 처리합니다.

제품 진단은 비동기 initiator stack을 최대 64프레임까지 판정하되 공개 좌표는 최대 8개만 남깁니다.
검증된 현재 번들과 일치한 frame만 `login_bootstrap` 또는 `login_submit`으로 분류합니다. URL, query,
요청 필드 이름과 값, 응답 값, header, 쿠키, requestId 원문은 저장하지 않습니다.

17:25:21 KST의 단 한 번의 관찰 결과는 다음과 같습니다.

1. 공개 키 GET은 HTTP 200·HTML이며 공개 호출 위치가 `login_bootstrap`으로 확인됐습니다.
2. 다음 공식 POST는 HTTP 200·JSON이고 공개 호출 위치가 `login_submit`, 요청 역할이
   `login_submission`으로 확인됐습니다.
3. 응답은 `dynaPathResultCode`, `errCode`, `errEngMsg`, `errMsg`, `globalFlag`, `requestId`라는 필드 이름만
   닫힌 스키마로 남겼습니다. 정확한 `errCode=macro_err1`은 로그에 값을 남기지 않고 `protection`으로
   변환했습니다.
4. 요청 본문은 보호 wrapper를 지난 형식을 안전한 파서가 해석하지 못해 `invalid`로만 기록했습니다.
   이는 입력 누락이나 자격증명 오류의 근거가 아닙니다. 요청 역할은 본문이 아니라 검증된 공개 호출 stack으로
   확인했습니다.
5. driver는 공식 세션 성공 근거가 없는 상태에서 `BrowserProtectionDetected`를 발생시켰고, 공유 쿨다운은
   `provider_access_restricted`로 열렸습니다.

이 결과로 “어느 요청인지 모르는 500”이라는 현재 진단 공백은 닫혔습니다. 다만 과거 10월 5일의 HTML 500과
이번 JSON 보호 응답이 같은 원인이라는 근거는 없습니다. 현재 차단을 없애기 위해 browser fingerprint,
입력 속도, header, SDK 동작을 흉내 내거나 보호 로직을 우회하지 않습니다.

Playwright 비교도 이 경계를 바꾸지 못했습니다. 서버 비교의 역할 미확정 공백을 Windows 호스트의
네트워크 전용 단일 제출로 보완한 결과, 새 자동화 profile은 입력·버튼·제출까지 정상이어도 같은 보호
응답으로 끝났습니다. 앞선 호스트 actionability 시간 초과는 `Debugger.enable` 계측 충돌이었고 페이지
결함이 아니었습니다. 따라서 “입력 방식을 바꾸거나 Playwright로 교체하면 된다”는 근거가 없습니다.
Selenium·WebDriver BiDi·Puppeteer도 새 자동화 세션이라는 경계를 바꾸지 않으며, Firefox·WebKit,
일반 사용자 profile 복사, `navigator.webdriver` 은폐나 OS 입력 흉내를 차례로 시험하는 방식은 보호 조건을
탐색하는 우회가 될 수 있어 후속 개발안으로 채택하지 않습니다.

대신 일반 Chrome에서 이미 성공한 세션을 읽거나 복사하지 않고, 앱이 소유한 live Chrome에서 사용자가 공식
화면에 직접 로그인하는 `dedicated_manual` 경계를 구현했습니다. adapter는 전용 marker·절대 경로·비공개
권한·GUI 조건을 모두 확인하며, 인증 header가 없으면 저장된 계정으로 자동 제출하지 않고 `auth_required`로
닫습니다. 다만 같은 credential generation의 browser와 보유 탭은 유지해 사용자가 그 live Chrome에서 로그인할
수 있게 합니다. 로그인 완료가 사용자 동작으로 새 탭에서 끝나 보유 탭의 header가 낡았을 때는 읽기 전용
공식 세션 확인의 양성 결과로 검색 화면을 갱신합니다. adapter는 새 로그인 탭이나 프로세스를 만들지 않고,
비인증·확인 불가이면 `auth_required`를 유지합니다. 같은 generation의 수동 인계는 일반 재사용 TTL·횟수
제한이 지나도 현재 live browser를 먼저 검사하고, 다른 generation은 대기 session을 폐기합니다. readiness와
공개 검색은 임시 profile로 분리합니다.

외부 요청 없는 Chrome 154 교차검증에서는 임시 전용 profile에 넣은 session cookie가 기본 정상 종료·재시작
뒤에는 1개에서 0개로 사라졌고, `--restore-last-session`을 양쪽 실행에 적용하면 1개가 그대로 복원됐습니다.
같은 임시 profile에 Playwright Chrome이 만든 가짜 loopback session cookie를 넣은 뒤 production Pydoll
Chrome에서 존재하는 것도 확인했습니다. 그러나 실제 앱 전용 Docker Chrome에서 직접 로그인한 KORAIL 세션은
첫 정상 종료·재실행 표본에서는 Pydoll과 일반 Chrome 모두 `로그인` 상태였습니다. 이후 장시간 수동 인계
표본에서는 TTL로 교체된 Pydoll Chrome이 같은 전용 profile의 실제 인증을 복원했습니다. 따라서 cross-process
복원은 가능한 fallback일 수 있지만 성공 조건이나 보장으로 사용하지 않습니다. bootstrap은 network 없는
one-shot initializer로 축소하고 adapter가 수동 로그인과 인증 확인의 단일 live process owner가 됩니다.

공개된 [승차권 진위 확인 API](https://www.data.go.kr/data/15099981/openapi.do)는 승차일 이틀 뒤부터
확인하는 사후 API이며 로그인·실시간 좌석·예약 기능을 제공하지 않습니다. [철도회원 안내](https://www.korail.com/ticket/membership/report/list)는
서비스 제공을 방해하는 반복 자동명령 프로그램을 이용 제한 사유로 명시합니다. 공식 연동 승인이나 제휴
계약이 없는 현재 상태에서 자동 로그인 보호를 우회하는 구현은 완료 조건이 아닙니다. 일반 Chrome·코레일
앱의 사용자 직접 이용과 기존 공식 HTTPS·앱 인계를 유지하고, 자동 연동은 운영사의 승인된 경로가 확인된
경우에만 재개합니다.

## 상주 세션 최신성 수정

설정 화면 controller는 다음 계약을 따릅니다.

- 런타임 조회 실패는 마지막 성공 snapshot을 현재 상태로 유지하지 않고 `상태 확인 실패`로 강등합니다.
- 15초 polling이 겹치더라도 가장 최신 요청 revision만 결과를 반영합니다.
- 계정 저장·교체·삭제 때 이전 runtime snapshot을 즉시 무효화합니다.
- 로그아웃 reset, polling 비활성화, 화면 unmount 뒤 도착한 응답은 버립니다.
- `ready`와 `locallyReusable`이 참이더라도 현재 계정 세대와 런타임 세대가 다르면 `계정 변경 후 재확인`으로
  표시합니다.
- 같은 세대의 후속 정상 응답이 오면 다시 `재사용 가능`으로 복구합니다.

KORAIL·SRT 공통 hook 회귀에서 조회 실패, 역순 완료, 저장 중 이전 응답, 삭제·reset·unmount 뒤 응답,
polling 중단과 후속 정상 복구를 확인했습니다. 320px 화면과 200% 확대에서 새 경고 문구가 가로 넘침을
만들지 않는 E2E도 통과했습니다.

## 공식 기능 복구의 완료 조건

서비스 health, 테스트 통과, 합성 응답, 공개 익명 시간표 성공만으로 실제 기능을 완료 처리하지 않습니다.
아래 순서는 같은 현재 계정 세대에서 차례로 확인해야 합니다.

1. 운영사 보호 대기 만료 외에 응답 상태 변화나 승인된 지원 조건을 먼저 확인한 뒤, 허용된 정상 흐름에서
   공식 인증이 성공하고 runtime이 같은 세대의 `ready`·재사용 가능 상태를 반환합니다.
2. 공식 예약·발권 내역을 읽어 필요한 과거 기록과 정확한 여정·열차·좌석 근거를 대조합니다. 인증·조회 실패나
   빈 목록만으로 예약 부재를 확정하지 않습니다.
3. 아직 출발하지 않은 새 승인 대상에서 `official_provider` provenance와 확인 시각이 있는 fresh 좌석을
   관측합니다. TAGO 시간표나 mock 결과를 좌석 근거로 쓰지 않습니다.
4. 동일 후보·episode·credential generation의 중복 차단을 유지한 채 예약 명령을 정확히 한 번만 실행하고
   결제 전에 멈춥니다.
5. 앱의 `payment_required`와 같은 대상의 정확한 공식 예약 상세를 대조합니다. 결제는 자동화하지 않습니다.

1단계는 2026년 10월 11일 두 경로로 완료했습니다. 먼저 `dedicated_manual`의 앱 전용 live Chrome에서
사용자 로그인 뒤 같은 계정 세대가 `authenticated`·`ready`·재사용 가능으로 전환됐습니다. 이어
`dedicated_auto`의 noVNC 없는 adapter·API 재생성에서 저장 계정 자동 로그인이 성공했고, adapter 단독
재시작 뒤에도 공식 세션이 자동 복구됐습니다. 새 임시 profile의 보호 원인은 여전히 미확정이며, 2~5단계와
승인된 미래 열차도 남아 있습니다. 그러므로 이 결과만으로 좌석 조회나 예약을 강행하지 않습니다.
