# 운영 장애 기록

운영 환경에서 실제로 발생한 장애와 그 해결 과정을 남깁니다. 재발했을 때 같은 진단을 다시 반복하지
않도록 증상, 근본 원인, 조치, 검증 근거, 남은 과제를 함께 적습니다. 최신 기록을 위에 둡니다.

## 2026년 10월 1일 · 직접 로그인 뒤의 P100 빈 목록과 조회 실패 재확인

### 로컬 설정 화면의 로그인 확인 실패

18시 32분 41초, 18시 33분 00초, 18시 33분 56초 KST의 로컬 설정 저장 요청은 모두
`PUT /api/v1/provider-accounts/korail` HTTP 503으로 끝났습니다. 같은 시각의 로컬 KORAIL adapter에는
`KORAIL login submission unavailable at stage=login_response`가 기록됐습니다. 앱의 관리자 로그인은
18시 32분 06초에 HTTP 200으로 완료됐으므로 이번 화면의 실패는 철도 계정 검증 단계에서 발생했습니다.
상단 `로그인 확인됨`은 이전에 저장된 계정의 검증 기록이며 이번 저장 요청의 성공을 나타내지 않습니다.

현재 기록만으로 이 세 요청의 상세 원인을 HTTP 500, 시간 초과, 여러 POST 관측 중 하나로 확정할 수
없습니다. 다른 진단 표본의 자동 제출 HTTP 500과 직접 입력 성공, 저장 비밀번호 일치도 각각의 근거로
유지합니다. 직접 입력 성공에서 공식 POST 두 개가 관측됐지만 역할이 분류되지 않았으므로 이를 이번
실패 원인으로 단정하거나 단일 제출 판정을 완화하지 않습니다.

다음 자연 발생 실패를 구분할 수 있도록 내부 예외와 sidecar 로그에 닫힌 관측 상태·실패 사유·HTTP 상태를
추가합니다. 자격증명·동적 주소·본문·쿠키는 기록하지 않으며 인증 판정, 공개 API, 계정 generation과
재시도 간격은 유지합니다. 코드 검증과 실제 인증 복구·재배포 결과는 따로 기록합니다.

진단 보완은 관련 5개 파일 261건, 마지막 fixture 정리 뒤 제출·transport 72건, 변경 source 3개의 strict
mypy와 변경 6개 파일의 Ruff E/F/I·format 검사를 통과했습니다. 겹치는 테스트 수를 합산하지 않습니다.
로컬 전체 `experimental-rail` 프로필의 `config --quiet`, 이미지 빌드와 강제 재생성은 성공했고 장기
서비스 12개 `healthy`, migration·log-init 종료 코드 0, 실행 adapter의 변경 source 3개 hash 일치를
확인했습니다. 배포 로그는 ignored `output/compose-login-diagnostics-*-local-*.log`에 남겼습니다.

18시 42분 58초 KST의 첫 자연 발생 예열 실패는
`stage=login_response state=failed failure=http_error status=500`으로 기록됐습니다. 이 새 표본은
여러 POST를 판별하지 못한 경우가 아니라 실제 공식 로그인 제출의 HTTP 500입니다. 같은 비밀번호의
직접 로그인 성공과 자동 제출의 차이가 생기는 정확한 입력·클릭 단계는 여전히 미확인이며, 실제 로그인
복구나 앞선 저장 요청 세 건의 상세 사유를 이 표본으로 소급 확정하지 않습니다.

이 비교 동안 서버는 DB·Redis·웹·proxy 네 서비스만 실행되고 API와 철도 호출 경로는 중지된 것으로
확인했습니다. 로컬 scheduler를 먼저 중지한 뒤 active·reserved·scheduled·rail queue·실행 중 예약이
모두 0임을 확인하고 전체 프로필을 정상 종료했습니다. 최종 실행 서비스는 빈 줄을 제외해 0개이며
데이터 volume을 보존했습니다. 후속 비교와 최신 이미지 준비 결과는 아래에 구분해 기록합니다.

전체 종료 명령은 `stop --timeout 60`으로 정상 종료했고, 빈 줄을 제외한 실행 서비스 0개도 별도로
재확인했습니다. 로컬이 중지된 뒤 새 Chrome 탭으로 같은 로컬 주소를 열었을 때 캐시된 현재 JS가
실행돼 AuthGate의 `서버 연결을 확인해 주세요`와 재확인 버튼이 표시됐습니다. 앱 실행 자체는 확인했지만
중지한 서버와 연결된 상태는 아니며, 이 확인 중 열차 조회·예약·계정 조작은 하지 않았습니다.

### 실제 로그인과 현재 공식 내역

17시 전후 사용자가 코레일 공식 홈페이지에 직접 로그인한 뒤 같은 브라우저에서 로그아웃 표시를
확인했습니다. 새 미결제 목록 화면의 자연 발생 `ReservationView` GET은 HTTP 200·정상 JSON으로
완료됐으며 `strResult=SUCC`, `h_msg_cd=P100`, `h_msg_txt=검색된 데이터가 없습니다.`와
`jrny_infos.jrny_info=[]`를 반환했습니다. 발권 화면에도 승차권이 없었습니다. 이전의 `P058` 인증
만료 관측과 다른 표본이며, 현재 사용자 브라우저의 공식 내역이 비어 있음을 확인한 결과입니다.

v1.2.8의 새 목록 observer는 정상 성공 조건을 빈 메시지 코드로만 제한해 이 `P100` 응답을 거부했습니다.
v1.2.9는 공식 화면에서 관측한 정확한 성공 코드·문구·빈 배열 조합도 받아들이도록 보완합니다.
현재 문서·단일 자연 발생 요청·완료 응답·안정된 DOM 조건은 유지하며, 같은 코드의 다른 문구,
비어 있지 않은 배열, 실패 결과·인증 만료·HTTP 오류를 부재로 처리하지 않습니다.

사용자 브라우저와 서버의 저장 계정 generation은 같은 것으로 확인되지 않았습니다. 이 내역 확인으로
서버의 기존 UNKNOWN 4건을 자동 해소하거나 재무장하지 않았고 새 예약·결제 요청도 0회입니다.
승인된 10월 2일 대전→서울 114편 22:42 일반실의 검증은 기존 계정 generation과 정상 재승인 조건,
새 공식 좌석 관측을 확인한 뒤에만 이어갈 수 있습니다.

그 뒤 Pydoll이 연 독립 Chrome의 공식 로그인 화면에서 사용자가 직접 입력하고 로그인한 결과도
확인했습니다. 관측한 공식 POST 두 개는 각각 HTTP 200·`text/html`로 약 125ms와 47ms에 응답했고,
로그아웃 표시를 포함한 정확한 인증 완료 header가 보였습니다. 두 요청의 역할은 분류되지 않았으므로
로그인을 두 번 수행했다고 기록하지 않습니다. 자동 입력 로그인·열차 조회·예약은 0회였습니다.
이 시점에는 사용자가 저장 비밀번호를 기억하지 못해 이번 입력과 저장된 값의 동일성이 미확인이었습니다.
이후 사용자가 숨김 입력 비교 도구를 직접 실행하고 `true` 결과를 알려 줬습니다. 도구는 세대 4의
저장값을 읽기 전용으로 비교했고 계정 정보를 저장하거나 교체하지 않았습니다. 사용자가 공유한 것은
일치 여부뿐이며 분석자가 실제 비밀번호를 읽거나 철도사에 입력하지 않았습니다. 사용자의 완료 결과에
근거해 저장값의 불일치 가설을 제외하며, 직접 입력 성공과 저장값 자동 제출 실패의 차이는 입력·제출
경로에서 더 확인합니다.

현재 관리자 API는 비밀번호를 보여 주지 않고 마스킹된 계정과 세대·인증·세션 상태만 반환합니다.
같은 값을 다시 저장해도 계정 세대가 증가하므로, 저장 계정을 갱신하는 행동을 기존 세대 4의 재검증으로
사용하지 않습니다. 동일 세대 재인증은 정상 provider session manager의 저장 자격증명 확인 경로이며,
세대가 달라진 기존 UNKNOWN의 자동 재확인이나 수동 재승인에는 연결 경로가 없습니다.

### 입력 방식의 로컬 비교

공식 공개 React 16·ReactDOM 입력 구조를 로컬 전용 페이지에서 재현해 가상 비밀번호 4개,
초기 입력값 2개, 입력 방식 2개의 16개 조합을 비교했습니다. 현재 production 제출 코드를 바꾸지 않고
실행했으며 모든 조합에서 입력 DOM 값과 React의 제출 상태가 일치했습니다. 실제 철도사 요청은
0회이고 사용자 비밀번호를 fixture에 사용하거나 원문 입력값을 진단 기록에 남기지 않았습니다.
이는 입력값과 React 상태가 어긋난다는 가설의 검증이며, 현재 근거로 입력 방식을 바꿔 로그인 500의
원인을 해결했다고 주장하지 않습니다.

### 같은 자동 입력 뒤 사용자 직접 클릭 비교

새 native Chrome을 proxy 없이 공식 LOGIN 주소로 직접 열었습니다. 앱의 production `clear`·`type`은
그대로 사용하고 자동 제출만 생략한 진단입니다. 아이디·비밀번호 입력은 `readonly=false`·
`disabled=false`였고 마우스 입력 모드는 꺼져 있었습니다. DOM의 두 입력값이 저장값과 같은지
비공개 비교한 결과는 모두 `true`였으며 원문을 기록하거나 계정을 다시 저장하지 않았습니다.

자연 발생 공개 키 GET은 HTTP 200이었고, `manual_wait` 단계에서 사용자가 공식 로그인 버튼을
직접 한 번 눌렀습니다. 공식 POST 1건은 HTTP 500으로 끝났고 화면에는 `통신중 에러발생`이
표시됐습니다. 진단 결과는 `official_http_error`이며 열차 조회·예약은 모두 0회입니다. 소유한 Chrome
프로세스를 관측·종료하고 lifecycle `CLOSED`를 확인했습니다. 앞선 사용자 직접 입력 성공 표본과
구분하며, 자동 클릭만이 실패 원인이라는 가설은 제외하지만 자동 입력·초기화 차이의 원인은 아직
확정하지 않습니다.

저장 계정 generation 4를 보존했고 저장·재저장은 수행하지 않았습니다. 실제 인증 `READY`, 공식 좌석
조회와 예약은 아직 확인 전입니다. 다음에는 빈 입력에서만 `clear`를 생략하는 진단 변형을 비교할
예정이며 가상 검증 79건과 준비만 완료했습니다. 실제 실행은 아직 하지 않았고 이번 HTTP 500 이후
최소 300초 대기를 지킵니다. 이 비교 실험을 확정 원인이나 production 수정으로 기록하지 않습니다.

### 로그인 뒤에도 남은 실제 열차 조회 실패

앞서 미결제 내역을 읽었던 일반 Chrome의 같은 로그인 세션에서 공식 메인 화면의 조건을
10월 2일 대전→서울 22시 성인 1명으로 선택하고
조회 버튼을 한 번 눌렀습니다. 자연 발생 업무 XHR은 HTTP 500·HTML 오류로 끝났고 통신 완료도
확인됐습니다. 공식 결과 화면에는 `운행하는 열차가 없습니다.`가 표시됐으나, 업무 요청이 실패한
표본이므로 실제 운행 없음이나 좌석 없음의 근거로 사용하지 않습니다. 공식 홈페이지 로그인은
정상이지만 이 세션의 조회는 실패했다는 사실을 구분합니다. 서버 IP·비밀번호·운영사 내부 장애를
원인으로 확정하지 않습니다.

앞선 16시 49분 익명 일반 폼 조회의 공개 multipart 필드도 직접 목록 조회 조건과 비교했습니다.
일반 폼은 공개 필드 24개·알 수 없는 필드 0개였고, 비교 대상 25개 조회 필드 중 18개 값이 같았습니다.
인원 0인 다섯 승객 필드와 `selGoSeat1`은 없었으며 열차 구분은 전체 `109`와 KTX `100`으로 달랐습니다.
`Device=BH`·`Version=999999999`는 기대값과 같았고 `spePersonnel`은 `[object Object]`였습니다.
로그인·예약 요청 없이 관측한 값의 일치 여부와 개수만 남겼으며 비밀값이나 원문 본문은 기록하지
않았습니다. 서로 다른 진입 경로의 공개 필드 차이를 확인한 것이며, 어느 차이가 HTTP 500의 원인인지는
확정하지 않았습니다.

### CI 실패와 검증용 데이터 교정

v1.2.8 커밋 `7a8b263`의 저장소 CI는 SRT 결제 완료 확인 테스트 한 건에서 실패했습니다.
결제 후 확인 정책은 보존된 좌석과 공식 내역의 정확한 일치를 요구하지만 해당 paid fixture에는
좌석 근거가 없었습니다. 테스트의 대상과 공식 내역에 같은 가상 좌석을 넣어 실제 정책을 충족하도록
교정했으며 생산 판정 정책은 바꾸지 않았습니다. 해당 파일 32건을 통과했습니다.

별도 브라우저 CI의 fullstack 흐름은 검증 페이지의 기본 달력이 2026년 7~8월에 고정돼 있어
10월 익일을 현재 활성 달력에서 선택하지 못했습니다. 조회 준비가 실패해 좌석의 `예매 가능` 표시도
나오지 않았습니다. 기본 달력을 KST 현재·다음 달로 만들고 공식 활성 월과 이전·다음 버튼 구조를
유지했습니다. 오류 시나리오의 고정 fixture는 보존했습니다. 브라우저 fixture 파일 70건을 실제
Chrome 27건과 단위 검증 43건으로 나누어 통과했고, 월말·연말 익일과 양방향 월 이동도 확인했습니다.

수정된 달력으로 격리 fullstack 브라우저 흐름 1건과 DB 상태 검증을 통과했습니다. 실행 스크립트
종료 코드는 0이고 Playwright의 최신 결과는 `passed`·실패 목록 없음입니다. 검증은 로컬 가상
철도사·별도 Compose 프로젝트에서 수행했고 예약 시도는 0건이었습니다. 생산 volume을 삭제하지
않았으며 실제 철도사 조회·예약 성공을 입증하는 검증은 아닙니다.

### 코드에서 확인한 결함과 수정

기존 네트워크 callback은 429와 최상위 문서의 403만 보존해 실제 검색 XHR의 500을 버렸습니다.
결과 대기에는 열차 행과 실패 근거가 모두 없어 타임아웃까지 기다렸고, 검색 조건별 30초 backoff만
적용했습니다. 다른 검색 조건과 활성 대기의 호출은 같은 실패를 계속 만들 수 있었습니다.

v1.2.4는 공식 HTTPS 호스트의 `/web_s/` business XHR·Fetch에만 500~599 근거를 남깁니다.
사진·폰트·분석 요청과 다른 호스트는 제외하고, 호출 제한·보호·명시적 점검 신호를 우선합니다.
이 근거가 있으면 일부 열차가 남아 있어도 `business_server_error`로 중단하고 기존 provider 조회 대기
정책을 적용합니다. 기본값은 300초이며 다른 조건의 시간표·좌석 조회도 기다립니다. HTTP 응답에는
`Retry-After`가 전달됩니다. 일반 결과 대기 타임아웃은 기존 조건별 backoff를 유지합니다.

진단에는 상태·resource 종류·닫힌 사유만 남기고 실제 요청 주소·본문·쿠키·인증값은 저장하지 않습니다.
검색 요청을 다시 제출하지 않으며, 예약 요청 뒤 실패는 기존 결과 불명과 공식 내역 확인 경계를 유지합니다.
기존 4건의 결과 불명 예약을 새로운 예약으로 다시 실행하지 않습니다.

  그 자식을 가리켜 팝업에 가려지지 않음을 확인했습니다. 좌석·예약 control은 누르지 않았습니다.
- 운영 Chrome 화면의 푸터가 v1.2.2로 표시되는 것을 확인했습니다. 394편의 기존 시도는 확인 시점에
  여전히 `unknown/inconclusive`, 자동 재확인 5회였습니다. 실제 새 예약 성공과 공식 내역 최종 확정은
  아직 검증하지 않았으며, 자연 발생 시도로 별도 확인해야 합니다.

## 2026년 9월 30일 · 공식 안내 팝업이 열차 목록의 더보기 클릭을 가림

### 증상과 재현

사용자 화면에서 2026년 10월 1일 대전→서울 12:00~18:00 시간표는 29편이 표시됐지만, 일반실·특실
58개가 모두 `서버 좌석 조회 미설정`으로 나왔습니다. Oracle API 컨테이너에서 같은 날짜·구간·시간으로
실제 `search_timetable`을 호출하자 약 24.9초 뒤 `KorailBrowserTimetableUnavailable`과
`source_unavailable`로 실패했습니다. sidecar 로그에는 같은 조회의
`result_expansion_stopped reason=repeated_window actions=1 rows=10`과
`provider_query_completed outcome=source_unavailable stage=expand_results_incomplete`가 남았습니다.

### 확인한 원인

좌석 조회 설정 누락이 아니었습니다. 운영 서버의 `experimental_rail_enabled`,
`korail_browser_adapter_enabled`, `korail_seat_monitoring_enabled`는 모두 `true`였고 내부 token도
설정돼 있었습니다. `/readyz`와 `/healthz`는 200, 로그인 예열은 `authenticated`였습니다. 장기 서비스
12개도 모두 `healthy`였습니다.

동일한 운영 이미지에서 로그인하지 않는 별도 읽기 조회로 DOM을 확인했습니다. 첫 열차 10개를 받은 뒤
`더보기`를 클릭해도 20초 동안 목록이 늘지 않았습니다. 클릭 위치의 `document.elementFromPoint`는
버튼이 아니라 공식 안내 팝업 안의 `IMG`를 가리켰습니다. 그 이미지의 대체 텍스트는
`10월 1일부터 승차권 예매기간 확대` 안내였고, 조상 요소에는 `layerWrap emer_pop`,
`ReactModal__Content`, `role=dialog`, `aria-modal=true`가 있었습니다. 팝업에는 `창닫기` 버튼과
checkbox가 있었습니다. 조회 경로가 이 팝업을 닫지 않은 채 아래쪽 `더보기`에 마우스 클릭을 보내
클릭이 안내 이미지에 막히는 것이 이번 재현의 직접 원인입니다.

미래 날짜 조회는 병결 열차의 정확한 식별자를 보존하기 위해 자정부터 공식 목록을 읽고 사용자 시간대로
거릅니다. 따라서 오후 조회도 초기 10개 이후의 목록 확장이 필요합니다. 확장이 실패하면 부분 목록을
공식 좌석 결과로 사용하지 않고 TAGO 시간표로 넘어갑니다. TAGO에는 좌석 재고가 없으므로 대기 등록도
열리지 않습니다.

화면의 `미설정` 안내는 별도의 진단 표현 문제입니다. TAGO 투영의 기본 사유인 `source_not_configured`가
공식 조회 실패 뒤에도 유지돼, 정상 설정된 서버가 설정되지 않은 것처럼 보입니다. 명절 이후 운행 중단이나
해당 날짜의 예매 불가를 뜻하는 근거는 이번 조회에서 확인되지 않았습니다. 팝업의 최초 게시 시점은
확인하지 않았으므로 장애 시작 시점과 명절의 관계를 단정하지 않습니다.

### 수정과 검증

- `korail_sidecar/pydoll/search_notice.py`에서 확인된 공식 안내의 구조·이미지 대체 텍스트·유일한
  `창닫기`를 검증합니다. 해당 안내만 한 번 닫고 실제 사라짐을 확인한 뒤 최신 목록을 다시 읽습니다.
  알 수 없는 팝업·변형 구조·복수 버튼·닫기 결과 불명은 조회 실패로 끝내며 checkbox는 바꾸지 않습니다.
  보호 신호가 있는 snapshot에서는 이 동작을 시작하지 않습니다.
- 공개 검색 폼과 결과 확장 경로에 이 처리를 연결했습니다. 안내 원문·DOM·URL을 운영 로그에 남기지
  않고 `event=search_notice_dismissed kind=booking_window_expansion`만 기록합니다.
- 공식 조회 실패 뒤 TAGO를 쓸 때 미관측 좌석에 검증된 실패 사유를 전달하도록 수정했습니다. 설정이
  꺼진 경우에는 `source_not_configured`, 조회 실패에는 `source_unavailable`, 보호 응답에는
  `provider_access_restricted`를 유지합니다. 미관측 좌석의 등록 행동은 계속 비워 둡니다.
- Oracle의 실행 중 서비스 코드를 바꾸지 않고 별도 임시 source와 로그인 없는 진단 브라우저로 수정본을
  먼저 확인했습니다. 같은 날짜·구간의 전체 목록을 확장한 뒤 요청 범위의 열차 53편과 오후 27편을
  약 13.4초에 반환했습니다. 일반실·특실에서 `available`, `limited`, `sold_out`,
  `standing_plus_seat` 상태가 확인됐고 진단 브라우저는 정상 종료됐습니다.
- 로컬 전체 배포의 첫 HTTP 조회는 11초에 오후 27편·공식 좌석 54개를 반환했지만, 이어지는 사용자
  화면 조회는 같은 목록 확장 실패로 끝났습니다. 재사용 브라우저에서 팝업이 첫 결과 snapshot보다
  늦게 나타나는 시점을 보완하기 위해 각 `더보기` 클릭 직전에도 현재 modal을 관측하도록 수정하고,

- 팝업 닫기→목록 확장 순서, 불명확한 팝업·버튼·응답 거부, 보호 snapshot 보존, 닫기 재시도 금지와

## 2026년 9월 23일 · KORAIL 브라우저 실행 실패와 부분 열차 목록 반환

### 확인한 증상

Oracle의 12개 장기 서비스는 모두 `healthy`였지만 KORAIL sidecar의 최근 공식 조회 4건은
`outcome=source_unavailable stage=browser_launch`로 끝났습니다. 로그인 예열도 같은 단계에서
반복 실패했습니다. API가 200을 반환한 사례가 있어도 이는 공식 조회 성공의 근거가 아닙니다. 공식 조회가
실패하면 TAGO 시간표로 넘어가는 경로가 있으므로, 그 응답에서는 공식 좌석 상태를 얻지 못합니다.

장애 당시 sidecar는 약 4.8GiB와 1,839개 작업 단위를 사용했고, 컨테이너 안에 며칠 전부터 남은 Chrome
실행 인스턴스가 여러 개 있었습니다. 서버의 여유 메모리와 디스크는 충분했습니다. 따라서 이번 표본의
직접적인 실패 지점은 공식 `서비스 연결대기` 화면보다 앞선 브라우저 실행 단계입니다.

### 원인과 조치

고정된 Pydoll 2.23.1의 `Chrome.__aexit__`는 CDP ping이 실패하면 Chrome 프로세스 종료를 건너뛰고
연결만 닫을 수 있습니다. 기존 lifecycle은 이 반환을 종료 성공으로 받아들여 브라우저 소유권을 버렸습니다.
남아 있던 Chrome 프로세스와 이 종료 경로가 맞물린 것으로 판단했습니다. 개별 프로세스 생성·종료 기록을
연결한 증거는 없으므로, 누적의 유일한 원인이라고 단정하지는 않습니다.

먼저 실행 중인 공식 조회가 없음을 확인하고 KORAIL sidecar만 정상 재시작했습니다. Chrome 자원 사용량은
약 0.7GiB·142개 작업 단위로 줄었고 로그인 예열은 `authenticated`로 회복됐습니다. 종료 코드에는
Pydoll의 종료 호출 뒤에도 자신이 소유한 Chrome 프로세스가 살아 있으면 이를 종료하고 임시 디렉터리를
정리하는 경로를 추가했습니다. 이 경로는 `event=browser_process_cleanup_fallback`으로 기록됩니다.

복구 직후 읽기 조회에서는 약 40초 뒤 열차 4편을 HTTP 200으로 반환했지만, 직전에
`event=result_expansion_stopped reason=repeated_window actions=2 rows=20`이 기록됐습니다. 당시 화면의
4편은 선택 시간 범위에 들어온 부분 목록일 수 있으므로 완전한 결과로 인정할 수 없습니다. 일반 성장 대기를
10초에서 20초로 늘리고, `서비스 연결대기` 안내가 한 번 보이면 잠시 사라져도 최대 480초까지 기다리도록
했습니다. 그래도 `더보기`가 남은 채 성장이 멈추면 공식 조회를 실패로 닫아 TAGO 시간표 fallback을
사용합니다. 부분 목록에 공식 좌석 근거를 붙이지 않습니다.

첫 재배포 후 같은 9월 26일 조회는 sidecar의 약 75초 provider deadline에 닿아 504로 끝났습니다. TAGO는
그 날짜의 서울→부산 시간표를 0건으로 반환했습니다. 이에 사용자 시간표 조회의 전체 예산을 최대 580초로
늘리고, 백그라운드 좌석 관측은 80초 상한을 유지했습니다. API의 HTTP 대기 상한은 600초입니다. 공식
대기 문구가 실제 화면에 나타나면 사용자 화면에 접속 대기 상태를 표시합니다. 공식 조회 실패 뒤 TAGO도
비어 있으면 빈 열차 목록 대신 503을 반환하도록 바꿨습니다.

### 검증과 남은 확인

- 종료 호출이 성공했지만 프로세스가 살아 있는 경우와 연결 정리가 실패한 경우의 회귀 테스트를 추가했습니다.
- 재시작 후 Oracle의 읽기 전용 서울→부산 9월 26일 09:00~12:00 조회는 약 40초 뒤 열차 4편을
  반환했지만 결과 확장 중단 로그도 남았습니다. 이 결과는 부분 목록일 수 있으며, 보호 화면 우회나
  자동 재시도는 하지 않았습니다.
- 두 번째 전체 `experimental-rail` 재배포에서 migration·log-init은 종료 코드 0, 장기 서비스 12개는
  모두 `healthy`였습니다. API의 적용 제한시간 600초, sidecar 제한시간 590초를 확인했습니다.
- 재배포 뒤 같은 읽기 전용 조회는 실제 `서비스 연결대기` 상태로 여러 차례 바뀐 뒤 약 54초에 공식
  열차 4편을 HTTP 200으로 반환했습니다. 해당 조회의 `provider_query_completed outcome=success`와
  `train_count=4`를 확인했고 `result_expansion_stopped`·`official_connection_wait_timeout`은 없었습니다.
  sidecar는 약 700MiB·116개 작업 단위였습니다. 대기열 표시의 sidecar 상태 전이는 확인했지만 실제
  로그인한 사용자 브라우저의 표시와 장기간 Chrome 프로세스 추이는 아직 확인하지 못했습니다.
- 전송 경계의 타입 검사 수정까지 반영해 전체 프로필을 다시 재생성했습니다. 이번에는 API 컨테이너에서
  실제 시간표 source를 호출하며 진행 상태를 함께 읽었습니다. `official_queue`와 `searching` 전이가
  전달됐고 약 63초 뒤 공식 열차 4편을 반환했습니다. 따라서 sidecar 내부 감지뿐 아니라 API의 상태
  전달과 긴 시간표 조회 경로까지 운영 환경에서 확인했습니다. 로그인한 사용자 브라우저의 화면 표시와
  장기간 프로세스 추이는 계속 운영 확인 항목입니다.

## 2026년 9월 18일 · 재사용 세션이 HTTP replay capture를 영구히 거부해 관측이 느려지던 문제

| --- | --- |
| 활성 대기 | 112건 |
| 노선·날짜 관측 그룹 | 3개 (대전→서울 9/20 80건, 수서→대전 9/19 16건, 대전→서울 9/19 16건) |
| 조회 1건 소요 | 15,365 ~ 18,831 ms |
| 실효 처리율 | 약 18초에 1건 |
| `next_check_at` 지연 | 50~100초 60건, 100~150초 35건, 150~200초 17건 |
| `capture_unavailable stage=capture_start reason=invalid_capture` | 185회 |
| `capture_suspended reason=repeated_replay_failure` | 5회 |

`query_backoff`와 `provider_query_skipped`는 0건이라 cooldown이 아니라 포화 상태였고, 조회 결과는 모두
`outcome=success`였습니다. 대기를 줄여도 KORAIL 호출은 3종류 그대로이므로 지연은 해소되지 않습니다.

### 근본 원인

`_PydollSession`은 공식 업무 조회 1회를 보장하려고 submit latch를 둡니다. `open()`은 이 latch를 지우지만
`navigate_fresh()`는 지우지 않고, `navigate()`가 다시 latch를 세웁니다. 그래서 직접 URL 경로로 한 번 조회한
session이 재사용되면 다음 조회의 `begin_http_replay_capture`가 항상 `invalid_capture`로 거부됩니다.

capture가 거부되면 lease가 설치되지 않고, lease가 없으면 search actor가 session을 폐기하지 않아 같은 session이
계속 재사용됩니다. 즉 한 번 실패하면 그 session의 수명(최대 100회 조회) 동안 replay가 되살아날 수 없는
자기강화 구조였습니다.

### 조치

재사용된 lease로 새 조회를 시작할 때 search actor가 `reset_search_state()`로 이전 조회의 latch를 먼저 지웁니다.
모든 조회 경로가 그 직후 탭을 교체하므로 "페이지당 공식 조회 1회" 보장은 그대로 유지됩니다. 세션 protocol에
`reset_search_state`를 추가하면서 browser composition shell의 줄 수 상한을 1,490에서 1,492로 올렸고, 나머지
표면 계약(정의 목록, 공개 84개·비공개 30개 이름 수)은 그대로입니다.

### 검증

재사용 session에서 두 번째 capture가 열리는지 확인하는 회귀 테스트를 추가했습니다. 수정을 임시로 끄면 이 테스트가
`['started', 'rejected'] != ['started', 'started']`로 실패하고 운영과 동일한
`capture_unavailable stage=capture_start reason=invalid_capture` 경고를 남기는 것까지 확인했습니다.

### 남은 과제

- 배포 뒤 실제 운영 표본에서 replay lease가 설치되어 관측 1건 비용이 브라우저 약 18초에서 replay 약 1초로
  내려가는지, `관측 지연` 안내가 사라지는지 확인이 필요합니다.
- 브라우저 전용 관측으로 되돌아가는 구간에서는 2초 목표와 30초 임계값이 여전히 달성 불가능합니다. replay 복구
  효과를 확인한 뒤 지연 표시 기준을 조정할지 결정해야 합니다.

## 2026년 9월 17일 · 로그인 세션 만료 뒤 재로그인이 15분 간격으로 늦어지던 문제

### 요약

KORAIL 로그인 세션이 끊긴 뒤에도 즉시 재로그인이 일어나지 않고, 재확인 간격이 1분에서 시작해 15분까지
벌어졌습니다. 설정 화면에는 `로그인 정보 확인 필요`와 `최근 재검증: 13분 전`이 남았고, 예약 시도로 감시가
`AUTH_REQUIRED`에 잠긴 대기는 다음 로그인 성공까지 재개되지 않았습니다.

### 증상과 타임라인

API 로그의 `Provider runtime prewarm completed provider=korail` 간격이 그대로 증상입니다. 시각은 KST입니다.

| 시각 | outcome | 직전 시도와의 간격 |
| --- | --- | --- |
| 17:02:19 | authenticated | - |
| 17:32:26 | failed (`stage=session_keepalive`) | 1807초 |
| 17:33:53 | auth_required | 87초 |
| 17:36:18 | auth_required | 145초 |
| 17:40:39 | auth_required | 261초 |
| 17:48:29 | failed | 471초 |
| 18:03:37 | failed | 907초 |
| 이후 | failed 반복 | 약 900초 고정 |

17:42:42에 `korail-browser-adapter`가 정상 종료 절차를 밟고 내려간 뒤 다시 뜨지 않아, 그 이후의 모든 시도는
`transport_error`로 끝났습니다. 컨테이너는 `restart: unless-stopped`라 명시적으로 멈춘 프로세스를 되살리지
않습니다.

### 근본 원인

어댑터 중단이 방아쇠였고, 세션 관리자의 네 가지 정책이 그 장애를 15분짜리 침묵으로 키웠습니다.

- 갱신을 만료 직전 120초에만 시도했습니다. 재사용 창이 1800초인 KORAIL은 인증 후 28분 동안 갱신 시도가
  아예 없었고, 유일한 시도가 만료 직전에 몰렸습니다.
- keepalive probe가 실패하면 같은 호출에서 새 로그인으로 넘어가지 않았습니다. 공식 `loginCheck`가 비JSON
  응답을 돌려주면 `BrowserSourceUnavailable`이 `prewarm_credentials` 밖으로 전파돼, 로그인을 한 번도
  시도하지 않은 채 실패로 끝났습니다. 로그의 `login prewarm unavailable at stage=session_keepalive`가 이
  경로입니다.
- 실패 원인을 구분하지 않고 60초에서 900초까지 같은 지수 backoff를 적용했습니다. 어댑터가 죽어 운영사에
  닿지도 못한 실패가, 계정 잠금 위험이 있는 자격증명 거부와 똑같이 15분씩 묵혔습니다.
- 저장된 `auth_required` revision은 자동 복구를 1회만 허용했습니다. 실패해도 DB의 `updated_at`이 바뀌지
  않으므로 revision도 그대로였고, 그 1회가 실패하면 자격증명 재저장이나 API 재기동 전까지 자동 재시도가
  멈췄습니다.

### 조치

- keepalive probe가 로그인 상태를 확정하지 못하면 폐기된 generation을 같은 호출 안에서 새 로그인으로
  대체합니다. 보호·호출 제한 응답은 그대로 전파해 차단 중 재로그인을 막습니다.
- KORAIL 갱신 창을 재사용 창의 25%로 앞당겼습니다. 최소 120초, 최대 600초, 창의 절반 이내로 제한하며 기본
  1800초 설정에서는 만료 450초 전부터 갱신합니다. SRT는 재사용 기한 기준 시각이 달라 같은 계산이 매 주기
  커지므로 120초 고정 창을 유지했습니다.
- backoff를 원인별로 나눴습니다. 자격증명 거부는 60~900초, 보호 응답은 900초를 유지하고, 운영사에 닿지
  못한 어댑터·DB 실패만 5~60초를 씁니다.
- revision당 복구를 자격증명 거부 기준 최대 5회로 늘리고, 보호 응답은 1회를 유지했습니다. 운영사에 닿지
  못한 실패는 이 예산을 소비하지 않으므로 어댑터만 복구되면 자동으로 재로그인합니다.
- 세션 관리자 주기를 30초에서 10초로 줄여 감지 지연을 낮췄습니다.

### 검증

- 어댑터 단위: keepalive probe가 `BrowserSourceUnavailable`을 던져도 같은 호출에서 재인증해 `READY`로
  끝나고, 새 generation이 이전 session을 대체하는 것을 확인했습니다. 보호 응답 전파 계약은 기존 테스트가
  그대로 유지합니다.
- 런타임 단위: 어댑터 장애 6회 반복이 복구 예산을 소비하지 않고(시작 6회, 판정 0회) 계속 재시도하는 것,
  자격증명 거부는 5회에서 멈추는 것, 보호 revision은 1회만 시도하는 것, 그리고 backoff가 5/10/20/40/60초와
  60/120/240/480/900초로 분리되는 것을 확인했습니다.
- 갱신 임계값: KORAIL 1800초 창에서 잔여 90초와 240초는 갱신하고 600초는 건너뛰는 것, 그리고 마지막 검증이
  5000초 지난 SRT session이 잔여 240초에서도 갱신되지 않는 것을 확인했습니다. 후자는 SRT에서 매 주기 로그인이
  반복되는 회귀를 막는 가드입니다.
- 운영 확인 필요: 실제 KORAIL 계정으로 세션이 만료되는 순간의 즉시 재로그인과, 어댑터를 내렸다가 올렸을
  때 1분 안에 복구되는지는 운영 환경에서 별도로 확인해야 합니다.

### 재발을 알아채는 방법

- API 로그에서 `Provider runtime prewarm completed provider=korail`의 간격이 계속 900초에 붙어 있으면
  자격증명이 실제로 거부되는 중인지, 어댑터가 죽어 있는지 먼저 구분합니다.
- `provider_sidecar_request_failed ... outcome=transport_error`가 쌓이면 세션 문제가 아니라 어댑터 가용성
  문제입니다. `docker compose ps`로 `korail-browser-adapter` 상태를 확인하고 다시 올립니다.
- 설정 화면의 `최근 재검증`이 계속 10분 이상으로 유지되면 복구 예산이 소진된 상태일 수 있습니다. 저장된
  인증 상태가 바뀌거나 자격증명을 다시 저장해야 자동 복구가 재개됩니다.

### 남은 과제

- `korail-browser-adapter`가 명시적으로 멈춘 뒤 되살아나지 않는 문제 자체는 이번 변경 범위 밖입니다.
  어댑터 가용성을 감시해 사용자에게 알리는 경로가 필요한지 검토가 필요합니다.
- 복구 예산 5회를 모두 소진했을 때 사용자에게 자동 복구가 멈췄다는 사실을 화면에서 구분해 보여줄지
  결정이 필요합니다.
- SRT의 갱신 창은 120초 고정으로 남았습니다. SRT는 재사용 기한이 `last_used_at` 기준이고 session을 재사용하는
  prewarm이 `last_verified_at`을 갱신하지 않아 telemetry 역산이 계속 커지며, 그대로 적용하면 10초마다 예열과
  DB 쓰기가 반복됩니다. sidecar 계약에 재사용 창 길이를 명시적 필드로 노출한 뒤 SRT에도 앞당긴 창을 적용할지
  결정해야 합니다.

## 2026년 9월 17일 · 공식 접속 대기 중 열차 목록이 잘린 채 완전한 결과로 반환되던 문제

### 요약

KORAIL은 접속이 몰리면 결과 화면 위에 `서비스 연결대기 중입니다` 안내를 띄웁니다. 이 안내가 떠 있는
동안에는 `더보기` 클릭이 먹지 않거나 응답이 늦어지는데, 확장 로직은 10초 안에 목록이 늘어나지 않으면
더 기다리지 않고 멈춘 뒤 그때까지 모은 목록을 완전한 결과처럼 돌려줬습니다. 중단 사실을 알리는 로그도
없어서 잘린 결과와 정상 결과를 구분할 수 없었습니다.

### 영향

- 열차 조회: 시간대 안 열차가 일부만 보이고, 화면에는 아무 경고 없이 `총 N개 열차`로 표시됩니다.
- 좌석 관측: 감시 중인 열차가 잘린 구간에 있으면 결과에서 찾지 못해 관측이 오류로 기록됩니다. 잘못된
  매진·잔여 상태로 확정되지는 않으므로 좌석 상태 자체는 fail-closed를 유지합니다.
- 오류 분류: 이때 남는 사유는 `provider_unavailable`이라 공식 출처 장애처럼 보이지만, 실제로는 목록이
  잘린 것입니다.

### 근본 원인

결과 확장은 `더보기`를 누른 뒤 목록이 늘어나기를 기다립니다. 이 대기 예산이 10초로 고정되어 있었고,
시간이 지나면 `stalled`, 화면이 그대로면 `repeated_window`로 판정해 확장을 멈췄습니다. 두 판정 모두
호출자에게 전달되지 않고 부분 목록만 반환됐습니다.

접속 대기 안내는 보호 marker 어디에도 없어 차단으로 분류되지 않습니다. 분류되지 않는 것 자체는
맞습니다. 보호조치가 아니라 기다리면 풀리는 줄서기이기 때문입니다. 문제는 그 상태를 `기다려야 하는
상태`로도 인식하지 못해 `멈춘 페이지`와 똑같이 취급한 점입니다.

### 조치

- 접속 대기 안내가 보이는 동안에는 10초 성장 예산 대신 전체 조회 예산까지 기다립니다. 줄이 풀려 목록이
  늘어나면 확장을 계속합니다.
- 확장이 목록 끝이 아닌 이유로 멈추면 `event=result_expansion_stopped reason=<사유> actions=<n>
  rows=<n>`을 남깁니다. `더보기`가 사라져 정상 종료한 경우에는 로그를 남기지 않습니다.
- 접속 대기가 조회 예산 안에 끝나지 않으면 `event=official_connection_wait_timeout`을 남깁니다.

### 검증

- 정상 상태의 실제 조회에서 대전→서울 09:00~18:00이 8회 확장으로 85행을 모두 불러오고 `더보기`가
  사라진 뒤 창 안 42편으로 정리되는 것을 확인했습니다. 화면에 보이던 42편은 잘린 값이 아니었습니다.
- 접속 대기 안내가 있는 화면에서는 10초를 넘겨도 기다렸다가 목록이 늘어나면 확장을 계속하고, 안내가
  없으면 종전대로 10초에서 멈추는 것을 단위 테스트로 고정했습니다.
- `더보기` 클릭 뒤 화면이 그대로일 때 잘린 정황이 경고로 남는 것을 단위 테스트로 고정했습니다.

### 남은 과제

- 잘린 목록을 화면에서도 알 수 있게 하는 일이 남아 있습니다. 지금은 로그로만 드러나므로, 사용자는
  목록이 완전한지 알 수 없습니다. API 응답에 목록 완전성을 실어 화면에 `일부 열차를 불러오지
  못했습니다`로 알리는 방식이 필요합니다.
- 실제 혼잡 시간대의 접속 대기에서 확장이 끝까지 진행되는지는 운영 표본으로 확인이 필요합니다.
- 초기 결과 대기(`wait_result`)는 접속 대기가 조회 예산을 넘기면 종전대로 실패로 끝납니다. 이 경계도
  접속 대기를 인식해 기다리도록 넓힐지는 실제 대기 시간 분포를 본 뒤에 정합니다.

## 2026년 9월 17일 · KORAIL HTTP replay lease 재생 불가로 인한 좌석 관측 대량 실패

### 요약

KORAIL이 좌석 조회 요청 URL을 일회성으로 바꾸면서, 브라우저에서 캡처한 HTTP replay 재료를 브라우저
밖에서 재생할 수 없게 됐습니다. 어댑터는 이 실패를 조회 전체의 실패로 승격해 30초 backoff을 열었고,
그 사이 예정된 관측이 모두 오류로 기록됐습니다. 공식 출처와 브라우저 조회 경로는 정상이었는데도
Oracle 운영 서버의 24시간 좌석 관측 오류율이 93.6%까지 올라갔습니다.

### 근본 원인

Pydoll 검색은 읽기 전용 브라우저 세션에서 공식 business 요청을 한 번 캡처한 뒤, 같은 route의 다음
조회를 그 재료로 재생해 약 1초에 처리합니다. KORAIL은 이 요청 경로를 페이지마다 달라지는
`/web_s/<무작위 경로>?_qzj=<일회성 토큰>` 형태로 바꿨고, 캡처한 URL은 그것을 만든 브라우저 페이지
밖에서 더 이상 유효하지 않습니다. 브라우저 밖 HTTP client로 재생하면 KORAIL이 HTTP 500과
`코레일 승차권예매` 오류 페이지를 돌려줍니다.

이때 replay manager는 이 실패를 typed source unavailable로 승격했고, sidecar의 search coordinator는
exact query에 30초 backoff을 열었습니다. 그 30초 동안 도착한 관측 요청은 전부
`event=provider_query_skipped reason=query_backoff`로 끝나 오류 관측이 됐습니다. 결과적으로 약 52초
주기마다 브라우저 조회 성공 1건과 오류 약 29건이 쌓였습니다.

정리하면 공식 출처 장애가 아니라 임대한 replay 재료만 못 쓰게 된 상태였는데, 그 하나가 정상 동작하는
브라우저 경로까지 막아 세운 구조적 결함이었습니다.

### 진단이 늦어진 이유

replay 실패 경로가 사유를 전혀 로그에 남기지 않았습니다. 남는 것은 상위의
`outcome=source_unavailable stage=http_replay` 한 줄뿐이어서, 캡처가 잘못된 것인지 응답이 깨진
것인지 공식 출처가 죽은 것인지 구분할 수 없었습니다. 실제 원인은 로컬 브라우저 어댑터 이미지에서
계정 로그인 없이 캡처-재생 흐름을 재현하고 원본 HTTP 응답을 직접 관찰한 뒤에야 확정할 수 있었습니다.

### 조치

`apps/api/src/rail_waitlist/korail_sidecar/pydoll/http_replay.py`에서 replay 실패를 lease의 문제로만
다루도록 바꿨습니다.

- invalid capture, invalid response, lease invalid, 일반 source unavailable은 기존 session invalid와
  같이 lease를 폐기하고 `None`을 돌려, caller가 같은 호출에서 cold browser 검색으로 관측을 끝냅니다.
- 실패 사유를 `event=cold_reinit source=http_replay reason=<reason> stage=<stage>`로 남깁니다.
- 이 fallback이 연속 3회 반복되면 `event=capture_suspended reason=repeated_replay_failure`로 900초
  동안 capture를 중단하고, 이후 `event=capture_resumed`에서 다시 시도합니다. 재생할 수 없는 lease를
  반복해 만들지 않기 위한 것입니다.
- 보호(protection), rate limit, 점검 판정은 종전대로 조회를 중단하고 provider cooldown을 엽니다.
  이들은 실제 운영사 신호이므로 브라우저로 우회하지 않습니다.

관측 1건의 비용은 replay 약 1초에서 브라우저 약 21초로 늘어납니다. 같은 route·날짜의 활성 대기는
coordinator의 단일 실행으로 한 번의 조회를 공유하므로, 실제 운영사 호출량은 오히려 줄어듭니다.

### replay lease 동작의 이전과 이후

replay lease는 읽기 전용 브라우저 검색 한 번에서 캡처한 공식 요청 재료를 출발·도착 route별로 임대해
두는 프로세스 내 자원입니다. 유효기간 1800초, 최대 재사용 100회, route별 bounded LRU라는 경계는
이번 변경에서 그대로입니다. 달라진 것은 재생이 실패했을 때 그 실패를 무엇의 실패로 볼 것인가입니다.

정상이던 시기(2026년 9월 12일 이전)에는 브라우저 조회 한 번으로 lease를 만들고 같은 route의 다음
조회 약 100회를 1초 안팎에 처리했습니다. 실제로 한 lease가 `lease_search_index=100`까지 쓰인 뒤
`lease_retired reason=search_limit`으로 정상 은퇴하고 새 lease로 넘어갔습니다.

KORAIL이 일회성 URL을 도입한 뒤에는 lease를 만들자마자 첫 재생이 실패했습니다. 이 실패가 조회 전체의
실패로 승격되면서, 못 쓰는 lease 하나가 정상 동작하는 브라우저 경로까지 30초 동안 막았습니다.

수정 뒤에는 같은 실패가 lease만의 문제로 한정됩니다. lease를 폐기하고 같은 호출에서 브라우저 검색을
이어가 관측을 정상으로 끝내며, 반복되면 캡처 자체를 잠시 멈춰 왕복 비용도 없앱니다.

| 구분 | 고장 이전(정상) | 고장 이후(수정 전) | 수정 이후 |
| --- | --- | --- | --- |
| 재생 성공률 | lease당 최대 100회 성공 | 0회, 첫 재생부터 실패 | 0회, 첫 재생부터 실패 |
| 재생 실패의 의미 | 드물게 발생, 대부분 session invalid | 조회 전체의 실패로 승격 | 임대한 재료만 무효 |
| 재생 실패 후 동작 | lease 폐기 후 브라우저로 회복 | 조회 중단, exact query에 30초 backoff | lease 폐기 후 같은 호출에서 브라우저로 회복 |
| 관측 결과 | 정상 좌석 상태 | backoff 구간의 관측이 모두 오류 | 정상 좌석 상태 |
| 실패 사유 로그 | 해당 없음 | 상위 `stage=http_replay`만 남고 사유 없음 | `cold_reinit ... reason=<reason> stage=<stage>` |
| 캡처 반복 | 필요할 때만 재캡처 | 사이클마다 못 쓰는 lease를 다시 캡처 | 연속 3회 실패 시 900초 캡처 중단 |
| 조회 1건 비용 | 약 1초 | 약 21초 성공 1건 + 오류 약 29건 | 약 21초, 같은 질의는 단일 실행 공유 |
| 보호·rate limit·점검 | 조회 중단과 cooldown | 조회 중단과 cooldown | 변경 없음, 그대로 중단과 cooldown |

KORAIL이 요청 URL을 다시 재생 가능한 형태로 되돌리면 `capture_resumed` 뒤 재생이 성공하면서 예전의
빠른 경로로 자동 복귀합니다. 이 경우 표의 첫 열 동작으로 돌아가며 별도 설정 변경은 필요하지 않습니다.

### 검증

- 재현: 로컬 브라우저 어댑터 이미지에서 계정 로그인 없이 대전→서울 조회를 두 번 수행해, 첫 번째는
  브라우저로 97편을 성공하고 두 번째 replay가 HTTP 500과 오류 페이지로 실패하는 것을 확인했습니다.
- 수정 확인: 같은 재현 흐름에서 세 번의 조회가 모두 실제 공식 결과를 반환하고, 실패한 replay는
  `cold_reinit` 뒤 브라우저 조회로 회복되는 것을 확인했습니다.
- 테스트: replay 계약 테스트를 추가하고 전체 pytest 4404건 통과와 mypy를 확인했습니다. SRT 예약 확정
  테스트 1건과 ruff 포맷 ratchet 실패는 이번 변경 전 HEAD에서도 같게 재현되는 기존 문제입니다.
- Oracle 재배포: `experimental-rail` 프로필 전체를 재빌드·재생성하고 migration 정상 종료와 장기
  서비스 12개 `healthy`를 확인했습니다. 배포 직후 20분 동안 좌석 관측 644건 중 오류 0건, 어댑터 조회는
  모두 `outcome=success`, TAGO fallback 경고 0건이었습니다.
- 로컬 재배포: 같은 커밋으로 `experimental-rail` 프로필을 재빌드·재생성하고 서비스 12개 `healthy`를
  확인했습니다. sidecar `/v1/seat-snapshot` 연속 호출이 모두 200과 31편을 반환하고, lease 생성 뒤 다음
  호출이 `cold_reinit`으로 회복해 성공으로 끝나는 것을 확인했습니다.

### 검증 중 관찰한 동일 계정 이중 실행

로컬 검증을 위해 `experimental-rail` 프로필을 올리자 로컬 어댑터가 KORAIL 로그인 프리웜을 수행했고,
Oracle과 로컬이 같은 계정의 세션을 번갈아 무효화했습니다. 양쪽 어댑터에
`login prewarm completed outcome=auth_required`가 반복되고, Oracle의 예약 확정이
`stage=confirmation_session_unavailable`로 실패했습니다. 좌석 조회는 로그인이 필요 없어 관측은 계속
정상이었고 오류는 전환 시점의 1분 구간에만 몰렸습니다.

이는 기존 운영 지침대로 같은 철도사 계정에서는 단일 활성 배포만 유지해야 한다는 것을 다시 확인해
준 사례입니다. 로컬 검증을 마친 뒤 로컬의 `experimental-rail`·`korail-browser-adapter`·
`srt-provider-adapter`를 정지·제거해 Oracle을 단일 활성 배포로 되돌렸습니다. 로컬에서 좌석·시간표
기능을 다시 확인해야 할 때는 Oracle 쪽 로그인·예약 경로와 겹치지 않는 시점에만 잠시 올립니다.

### 재발을 알아채는 방법

sidecar 로그에서 다음 순서를 봅니다.

- `event=cold_reinit source=http_replay reason=source_unavailable`이 반복되면 replay 재료가 다시
  재생 불가 상태입니다. 이 자체는 관측 실패가 아니며 브라우저 조회로 회복됩니다.
- `event=capture_suspended`가 열린 뒤에는 브라우저 조회만으로 관측이 이어져야 합니다.
- 그런데도 `outcome=source_unavailable`과 `event=provider_query_skipped reason=query_backoff`가 쌓이면
  그때는 브라우저 경로까지 실패한 것이므로 공식 출처 장애로 다룹니다.

### 남은 과제

- 대시보드의 24시간 누적 좌석 관측 오류율은 과거 오류가 빠질 때까지 높게 보입니다. 실제 운영 표본에서
  정상 범위로 내려가는지 확인이 필요합니다.
- 브라우저 전용 관측으로 전환된 상태에서 같은 route·날짜 활성 대기가 coordinator 단일 실행을 공유해
  `next_check_at`이 계속 전진하는지, 관측 주기가 길어진 것이 알림 적시성을 해치지 않는지 확인이
  필요합니다.
- TAGO fallback의 좌석 미관측 사유가 `source_not_configured`("서버 설정을 확인하세요")로 표시됩니다.
  실제로는 설정 문제가 아니라 일시적인 공식 조회 실패이므로 문구가 오해를 줍니다. 실제 실패 사유가
  전달되도록 고치는 것이 남아 있습니다.
- KORAIL이 일회성 URL을 되돌리면 `capture_resumed` 뒤 replay가 다시 성공하며 자동으로 빠른 경로로
  돌아옵니다. 별도 조치는 필요하지 않습니다.
